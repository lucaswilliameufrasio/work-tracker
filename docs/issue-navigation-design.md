# Private project and issue reading journey

Slice230 joins the implemented reads into a deliberately read-only browser journey: explicit member opens `/projects`, chooses an accessible project, pages `/projects/{uuid}/issues`, and opens `/projects/{uuid}/issues/{number}` for detail and a bounded journal page. Normal links preserve browser history; detail links carry the originating issue-list cursor for a predictable back link. Project archive inclusion is explicit and resets pagination. Missing/inaccessible resources share an unavailable state;401 clears data and asks for a new session without enabling login. No data or bearer is stored in browser storage.

Routes are parsed strictly before requests. A typed project client uses the existing accessible-project API, never the operational admin catalog. One discriminated-union workflow holds idle/loading/ready/suspended/signed-out/unavailable/read-error; only ready owns private view data. Loading a new page replaces, rather than appends, old records. Read failures discard data. Abort/generation guards ignore obsolete completions, including dispose. Blur, hidden and pagehide synchronously clear DOM via flushSync. Focus/visible/persisted pageshow coalesce a read-only refresh. Private HTML GET/HEAD is no-store for the entire projects route family. These event seams do not certify physical BFCache or every browser engine.

Detail loads its record, journal page and the first100 include-archived statuses/types concurrently, with a whole-view eight-second cancellation deadline. Each server request independently revalidates its own transaction; the composite view is not an atomic multi-request snapshot. Verify journal issue IDs match detail and scope. Metadata pages are explicitly partial: unresolved names remain labeled as unloaded references, not invented names, hidden rows or authority. Future targeted catalog lookups/full catalog navigation remain separate. Never auto-traverse arbitrarily large catalogs. Description is escaped plain Markdown source, explicitly labeled; no HTML, images, remote fetches or Markdown renderer are enabled. CommonMark rendering and complete catalog-resolution UX remain pending.

Visual plan: keep the existing Puxiri Inter type and tokens (light background #f7f8f5, white surface, text #17231c, muted #506357, green #245c3a; dark equivalents already defined). Use a compact work index, not a marketing hero or dashboard card grid: project key/issue key beside readable titles, modest separators, one bounded page at a time and clear next-page action. Detail is a reading column with title, priority, due date, resolved status/type and a separate journal section. Align left, wrap long untrusted text, keep44px targets and visible focus. No new fonts, palette or motion. The generic design-system search suggested storytelling/motion/handwritten fonts, which do not fit this internal work journey; rejected in favor of the established system. Svelte guidance confirmed semantic nav/main/button elements. Mobile uses the same reading order without horizontal overflow.

Verification includes workflow/route/parser tests and actual Chromium HTTPS with synthetic migrated SQLite data, desktop light/mobile dark, bounded pagination, detail/back, hostile Markdown displayed as text/no external requests, empty/unavailable/signed-out states, synchronous concealment and revoked-session refresh. Existing session screen remains unchanged. This read journey does not complete board/filter/search/mutations/idempotency/outbox/live updates, login/setup, backup or release gates.

Follow-up slice231 supersedes the first100 catalog strategy above with [one-record resolution](project-catalog-detail-design.md): read issue first, then journal and its two exact referenced records concurrently. Archived references beyond the first100 entries resolve without traversal or unloaded-name fallback. The per-request snapshot and whole-view deadline limitations remain.
