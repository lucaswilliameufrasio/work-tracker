# Bounded board screens and constrained issue movement

Slice233 composes the existing board reads into `/projects/{uuid}/board` and a focused `/projects/{uuid}/board/{status_id}`. The overview reads four status candidates from the current UUID-keyset catalog page, filters visible statuses and orders that page's columns by position/id, then requests at most20 cards per column. At most four column requests/80 cards are materialized. A page may contain no visible candidates; do not silently traverse further or claim the whole board is empty. Explicit next-status-page navigation preserves the catalog boundary. This is bounded catalog traversal, not global position-keyset pagination after future arbitrary status reorder; full-board ordering across large reordered catalogs remains a follow-up.

Each column shows its authorized nontrash total, ordered cards and a link to continue reading that column in a focused paginated view. The Slice233 baseline had no drag/drop, mutation, filters, optimistic update or SSE. Slice247 layers explicit, keyboard-accessible move controls over this bounded read: they can target only a visible column and place a card at its top. Cards link to the existing detail; normal browser navigation preserves the focused URL/cursor. Preserve existing Puxiri tokens and reading order, visible keyboard focus and44px targets; columns wrap on wide screens and stack on mobile, rather than requiring horizontal scroll.

Typed client validates every card's project/status, existing summary allowlist, signed-i64 decimal rank, strict rank/id order, unique IDs, bounded page size, nonnegative-i64 count >=page length and consistent full-page continuation. The next cursor must decode to the last returned rank/id. Reuse cookie-only streaming transport and safe errors; no retries/traversal/storage. WorkScreen's whole-view deadline, generation/cancellation, synchronous concealment and current-access refresh apply unchanged. Independent API reads remain separate snapshots, not atomic composite state.

The original read-only evidence includes parser/error tests, actual Node→HTTP/SQLite pagination and denied sessions, plus Chromium HTTPS desktop/mobile overview/count/ordered cards/focused continuation/detail and private-session lifecycle. Slice247 separately adds SQLite/router mutation tests and an HTTPS Chromium movement/replay journey; those synthetic fixtures do not prove production capacity or outbox delivery. Global ordering after arbitrary status reordering, filters, live updates and release gates stay open.

Slice234 supersedes UUID-catalog traversal/local sorting above with [globally position-ordered visible board metadata](board-status-pagination-design.md). The overview retains its four-column/20-card budgets but no longer filters hidden candidates or sorts a UUID subset. Position changes between requests still do not create a frozen snapshot; no status editor is introduced.

Slice247 adds `POST /api/v1/projects/{project_id}/issues/{issue_number}/move`. Its strict body contains the expected issue version, target status UUID and optional adjacent issue UUIDs; rank is never accepted from the client. `BEGIN IMMEDIATE` revalidates session, current `MutateIssues` authority, project/issue eligibility, visible target status and neighbor adjacency, then atomically allocates or rebalances rank, updates completion time/version, writes a content-free `issue.moved` history event and outbox envelope, and stores an immutable idempotency receipt. Effective no-ops receive stable receipts without version/history/outbox changes. Replay returns the original receipt only after current authority and issue eligibility are revalidated. A stale version or changed boundary requires a board refresh; uncertain results are replayed explicitly with the same key and byte-equivalent command.

The current UI intentionally exposes only “move to the top” for a column represented on the bounded board page. It refreshes the board only after confirmed success and never updates optimistically. The server contract supports other adjacent placements, but drag/drop, arbitrary client rank, cross-page destination discovery, filters, live updates and outbox consumers are not introduced here. The HTTPS browser test loses a committed response, replays the same key, verifies the card in the destination and restores the fixture state; this is local synthetic evidence, not provider-live or production-readiness evidence.
