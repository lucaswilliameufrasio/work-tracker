# User session management — feature design

**Status:** Domain listing/revocation and opt-in authenticated current-session/list/individual/global-revoke HTTP are implemented; UI remains pending.
**Requirements:** `docs/development-plan.md`, sections 7.2 and 19.2.

`SessionStore::list_active` returns only sessions owned by the supplied authenticated user that still pass the same active-account, timestamp, absolute-expiry, and inactivity checks used for token validation. It marks the current session by opaque session ID and returns creation, activity, and expiry timestamps. It never returns token digests or bearer values, and this schema does not collect IP address, user-agent, or device fingerprint metadata.

Expired, revoked, malformed, future-dated, and otherwise invalid rows are omitted rather than exposed as active. Session revocation is already owner-scoped; global revocation ends every session for the user. The HTTP adapter must derive the user/current session only from a validated cookie, never request input, and use generic not-found behavior for a foreign session ID.

`DELETE /api/v1/auth/session` (slice216) validates the exact cookie plus Origin/CSRF and derives the revoked user/session inside the same write transaction as audit. It clears the cookie only after commit and leaves other sessions intact. See [session logout](session-logout-design.md). Slices218–219 extend termination and listing as documented below. The product still needs the “My sessions” UI with current-session labeling and explicit confirmations. Whether to capture coarse device metadata is a product/privacy decision and is intentionally not guessed here.

## Individual/global revocation contract — 2026-10-19

Slice218 adds opt-in `DELETE /api/v1/auth/sessions/{session_id}` and `DELETE /api/v1/auth/sessions`. Both use the existing same-origin/CSRF transport boundary and revalidate the exact bearer/account/deadlines in the write transaction. Ownership comes only from that validation, never from request IDs. Individual targets must be canonical UUIDs; foreign, missing and already-revoked targets share a generic 404. Successful individual revocation returns 204 and clears the cookie only when the target is the current session. Global revocation includes the current session, returns 204 and clears the cookie only after commit. Both preserve other users' sessions and atomically append the existing content-free audit event; audit failures roll back all revocations. Concurrent global requests using the same bearer cannot both succeed after the first invalidates it.

These are self-service termination actions, not grants of privileged assurance; they do not require or create a reusable MFA proof. No query options or caller-selected user IDs are accepted. A valid session may revoke an expired but not-yet-revoked owned session. The ID-based internal APIs remain for existing trusted flows; HTTP must not call them outside the new session-bound operation. Session-list pagination and UI confirmations remain separate follow-up work, not fulfilled by these routes.

## Bounded session-list contract — 2026-10-19

Slice219 adds opt-in `GET/HEAD /api/v1/auth/sessions`, retaining DELETE on the collection. Only `page_size` (default50, range1–100) and `cursor` (canonical UUID) are accepted. Identity and collection data share a single read snapshot; request preflight activity touch remains separate and is not authorization for the read. Results contain only `id`, `created_at`, `last_activity_at`, `expires_at` and `is_current`; no user ID, token/digest, IP, user agent or reusable assurance is returned.

Use an indexed `(user_id, id DESC)` keyset over non-revoked rows, with at most `page_size + 1` rows materialized. Order is descending **session record ID**, not last-activity or original authentication time: UUIDv7 records are newly minted on MFA rotation even when original lifetime/creation is preserved. The boundary need not identify an existing/owned row, and grants no authority; every query still restricts ownership to the current bearer-derived user. Revoking/deleting the boundary does not break continuation. A new read revalidates auth, and a cross-page traversal is not a frozen snapshot.

Expired, idle, future-dated, malformed-timestamp and otherwise invalid rows are filtered with the existing session validation policy **after the bounded fetch**. Consequently a page may be short or empty with `has_more=true`; its cursor advances past the last examined candidate, not the last returned valid item. Consumers must follow `next_cursor` until `has_more=false`. This deliberate contract avoids an unbounded scan to fill a page of valid sessions. A malformed stored record ID fails closed as a generic storage-data error rather than emitting an unusable cursor. Missing optional cursor is omitted, never JSON null. No device metadata collection, cleanup job, active-session cap, rate-limit policy or UI is selected by this query contract.
