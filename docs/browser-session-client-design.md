# Browser session client boundary

Slice222 introduces the client used by the slice223 [My sessions screen](session-screen-design.md), without enabling login/setup. Use fixed same-origin relative API paths and native fetch with same-origin credentials/mode, no-store, redirects refused and caller cancellation plus an eight-second client deadline. The browser manages the HttpOnly cookie; client code must never read/write the bearer, Cookie/Origin headers, localStorage or sessionStorage. Slice223 adds controlled local HTTPS Chromium evidence for native cookie/Origin behavior; other engines, cross-site matrices and production proxy/TLS acceptance remain separate gates, not something to fake in production code.

Validate response JSON from `unknown`, cap collected response bytes at64KiB, accept only the documented fields/types/canonical IDs/UTC timestamps and enforce page-size/cursor progression. Empty candidate pages with continuation are valid; do not fetch all pages automatically. Keep error presentation generic, with safe status/code/request_id/retryable fields instead of reflecting raw response bodies/messages. Server `retryable` is guidance, never permission for an automatic mutation retry.

Before each explicit termination command, fetch current-session/CSRF afresh, then send one bodyless DELETE with that CSRF value. Never automatically replay after a network loss, timeout, rotation mismatch,403 or ambiguous committed response. A cookie rotation between the read and write may fail closed; UI must refetch current state before another deliberate action. No client timeout can guarantee a mutation was not committed. Client-only input rejection must occur before fetching.

“No automatic replay” is an application-code rule, not a guarantee of one wire transmission by native browsers or proxies. Slice223 observed Chromium retransmitting a bodyless DELETE after pre-header connection loss. Server-side session ownership/revalidation/atomic revocation and audit must remain replay-safe; UI must handle either an unconfirmed result or a later401 without repeating a command itself. See `session-screen-design.md` for the controlled fault matrix.

Tests cover parsers/request construction/cancellation, body limits, malformed/error responses, candidate pagination and one-shot mutations. A Rust integration fixture must seed only temporary SQLite/synthetic sessions and run the TypeScript client through real loopback HTTP. Its Node-only fetch adapter supplies the synthetic cookie and configured Origin because Node is not a browser cookie jar; this is not evidence for actual Secure/SameSite storage, browser CORS/Origin behavior, UI confirmations or public/provider access. The adapter must stay in test code, never the production client.
