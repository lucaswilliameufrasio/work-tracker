# Private issue creation journey

Follow-up239 replaces the initial HEAD read proof with the [advisory session-bound mutation capability projection](project-capabilities-design.md). Known read-only access no longer mounts a form or retry control. The POST remains the independent authorization boundary; the rest of the lifecycle/key preservation design below is unchanged.

Slice238 adds `/projects/{uuid}/issues/new` as a separate create screen, not an editor in the board or detail screen. Entry links from issue lists/boards and eligible project cards. No assignee picker without a project roster API: initial form is title and optional plain Markdown-source description, with server-selected task/todo defaults. Existing typography/colors/responsive spacing remain; associated labels, inline errors, live status, focus heading on transitions and44px actions support keyboard/mobile use. No Markdown preview or unsanitized HTML.

Check current-session then HEAD issue collection with page_size1 (read membership proof, no response content). This does not claim mutation capability: server revalidates active member/manager/archive/defaults at commit. Readable viewers/archived projects may reach a form by direct link but receive generic rejection on submit; the UI must explicitly explain that creation permission is checked on send, not infer permission from organization authority. Do not walk arbitrary project catalog pages to infer access. Route/query selectors are strict; no private text or keys in URLs.

Controller uses a discriminated state union, one generation and cancellable operation. Draft values live only in the mounted form and are discarded on blur/hidden/pagehide; DOM is removed synchronously with flushSync. On submit validate once, snapshot raw title/description and generate one UUID, retaining command/expected actor only in memory for the page lifetime. Pending/uncertain commands cannot be edited or replaced with a new key. A single explicit re-send uses exactly that command/key; no auto-retry on focus/start/refresh, failures, Retry-After or abort. A failed/unknown response is conservatively unconfirmed; inform user it may have committed, offer same-request confirmation and list navigation, never claim rollback. Success displays only stable receipt/link, not retained free text, and clears command. Starting another issue after known success is an explicit new-page action.

Suspension aborts transport and hides all private state immediately. If submission was pending, retain only the original in-memory command as uncertain; ignore late completion by generation. Returning rechecks current session, same actor and read access before showing uncertain controls or a confirmed reference; it never resumes POST. Identity/access/session failure hides the command without transferring it to another principal. Dispose clears it. No storage/service-worker cache/logging or process-survival draft guarantee; reload/navigation loses unconfirmed keys, so warn before leaving the unconfirmed screen without introducing browser modal dialogs. This does not certify physical BFCache behavior or other browser engines.

Verification: pure controller tests for duplicates/replay/lifecycle/late completions/identity/access failures, real HTTPS Chromium desktop/mobile form→router→SQLite issue/history/outbox/receipt, concurrent-submit prevention, uncertainty/replay and private DOM concealment, plus full repository gate. Existing read journeys remain unchanged. More precise pre-submit mutation capability, richer fields, persisted draft recovery, live providers, outbox delivery and production auth/release remain separate work.
