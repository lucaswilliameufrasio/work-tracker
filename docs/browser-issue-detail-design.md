# Bounded issue detail and history reads

Slice226 adds opt-in `GET/HEAD /api/v1/projects/{project_id}/issues/{issue_number}` and the `/history` subresource. The detail returns a flat issue record (summary plus optional description/completed_at/trashed_at), never an embedded unbounded journal. History returns the normal bounded page envelope. Both require current session identity and explicit project read access in the same read transaction; authorized direct reads include retained trash and archived projects. Missing/inaccessible project or issue remains generic404.

Preserve the existing ID-based internal detail method and its full-history behavior for its trusted callers, but do not expose that potentially unbounded method to HTTP. Extract a transaction-owned record reader; it validates one bounded creation event as an integrity prerequisite, not every future history row. Historical event pages validate the rows they actually return. Description stays bounded by the domain's64KiB byte limit and is JSON data, not rendered HTML. The route permits no query options for the detail; history accepts cursor/page_size1–100/default50 only. Issue numbers/versions retain the slice225 canonical decimal-string contract.

History order is `(occurred_at ASC, id ASC)` with keyset continuation over the existing project/issue/time index. The opaque cursor encodes canonical UTC-nanosecond timestamp plus canonical event UUID as Base64URL without padding, with strict length/re-encoding checks before decoding. A boundary need not still exist and grants no access; every page revalidates session/project. Public history pagination fails closed on selected noncanonical persisted timestamps rather than emitting an unusable boundary. This contract matches application-generated timestamps; no silent migration or normalization of old data is performed. Multi-request traversal is not frozen.

No writes, timeline UI, Markdown rendering, search/board, API-token/MCP access or login/setup is added. Functional history remains content-free actor/event/time data, not issue description snapshots. These endpoints do not complete the Kanban journey or approve external/provider/release gates.

The current migrated schema supports only a unique `issue.created` event per issue. Tests preserve that invariant rather than rebuilding the journal or fabricating production-supported update events to manufacture long pages. Cursor seek, strict validation, scoping and empty continuation are exercised with real migrated data; multi-event lookahead/large-journal capacity must be revalidated when real mutation events and their schema are introduced. SQL already uses the bounded limit and existing composite index; no migration is relaxed for this slice.
