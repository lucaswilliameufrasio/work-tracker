# Audit events — feature design

**Status:** Minimal transactional audit records are implemented for email address changes and confirmation, password reset/change, session revocation, project creation, and project/organization membership changes. HTTP administration, audit browsing/retention, and failed-attempt recording are not implemented.

**Requirements:** `docs/development-plan.md`, sections 5, 6, and 13.

`audit_events` stores an allowlisted event kind, success/failure result, optional actor user ID, opaque target kind/ID, and UTC timestamp. Project-membership events additionally store the affected `subject_user_id` and typed before/after project roles. Organization-membership events target the affected user and store the same user as `subject_user_id`, with typed before/after organization roles. Non-membership events require all subject/role fields to remain empty. The schema rejects unknown kinds, outcomes, targets, and invalid role transitions; update and delete triggers make records immutable. There is no arbitrary details/payload column, so callers cannot attach passwords, tokens, email addresses, issue content, or provider responses.

Mutation hooks append the success event to the same SQLite transaction as the protected write. This applies to email address add/confirm/promote/remove, password reset/change, session revoke/revoke-all, project creation with its initial manager membership, project-member add/role-change/remove/self-leave, organization role changes, both sides of ownership transfer, and organization-member removal with every affected project-membership removal. Membership events retain only the affected user and typed role transition; self-grants and self-exits are distinguishable because actor and subject match. If writing any audit event fails, all protected membership changes in that operation roll back. Password changes require the caller to supply an explicit optional actor separately from the target user.

Current mutation hooks record successful committed operations only. An operation rejected or rolled back is not represented as a failed audit event; a future HTTP/security-attempt audit path must define its own transaction and privacy semantics rather than weakening atomicity of these records. No audit query/UI, actor authorization policy, retention/cleanup, or export exists yet.

Integration tests cover schema constraints, immutability, caller-owned rollback, successful password-change, project-creation, project-membership and organization-membership audit, and rollback when audit persistence fails. Migration 0013 extends project targets; migration 0023 preserves prior rows while adding constrained project-membership subjects and role transitions; migration 0024 preserves those rows while adding constrained organization-membership role transitions.
