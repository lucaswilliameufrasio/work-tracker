# Audit events — feature design

**Status:** Minimal transactional audit records are implemented for email address changes/confirmation, invite-only registration, account ban/unban, password reset/change, session revocation, project creation, project/organization membership changes, and organization invitation lifecycle events. HTTP administration, audit browsing/retention, and failed-attempt recording are not implemented.

**Requirements:** `docs/development-plan.md`, sections 5, 6, and 13.

`audit_events` stores an allowlisted event kind, success/failure result, optional actor user ID, opaque target kind/ID, and UTC timestamp. Project-membership events additionally store the affected `subject_user_id` and typed before/after project roles. Organization-membership events target the affected user and store the same user as `subject_user_id`, with typed before/after organization roles, including first membership addition. Invitation lifecycle events target an opaque invite ID; invitation email and token never enter the audit row. Account status events target the opaque user ID; `auth.user.banned` alone may carry the required trimmed, single-line ban reason, constrained to 1–500 characters. The operator must not put secrets or unnecessary personal/content data in that field. Other events require the reason and membership fields to remain empty. The schema rejects unknown kinds, outcomes, targets, and invalid role transitions; update and delete triggers make records immutable. There is no arbitrary details/payload column, so callers cannot attach passwords, tokens, email addresses, issue content, or provider responses.

Mutation hooks append the success event to the same SQLite transaction as the protected write. This applies to email address add/confirm/promote/remove, invite-only account registration (email-added, email-confirmed, password-changed, invitation-accepted, and membership events), account ban/unban, password reset/change, session revoke/revoke-all, project creation with its initial manager membership, project-member add/role-change/remove/self-leave, organization membership add/role change/removal/self-exit, both sides of ownership transfer, invitation issue/reissue/cancel/accept, and all affected project-membership changes. Membership events retain only the affected user and typed role transition; self-grants and self-exits are distinguishable because actor and subject match. A ban audit reason and all account/session/token invalidations share the account-state transaction; unban records no reason and does not restore credentials. If writing any audit event fails, all protected account, credential, session, membership, and invitation changes in that operation roll back. Password changes require the caller to supply an explicit optional actor separately from the target user.

Current mutation hooks record successful committed operations only. An operation rejected or rolled back is not represented as a failed audit event; a future HTTP/security-attempt audit path must define its own transaction and privacy semantics rather than weakening atomicity of these records. No audit query/UI, actor authorization policy, retention/cleanup, or export exists yet.

Integration tests cover schema constraints, immutability, caller-owned rollback, successful password-change, project-creation, project/organization membership, invitation lifecycle, invite-only registration, account ban/unban audit, and rollback when audit persistence fails. Migration 0013 extends project targets; migration 0023 preserves prior rows while adding constrained project-membership subjects and role transitions; migration 0024 preserves those rows while adding constrained organization-membership role transitions; migration 0025 adds organization-member addition and invitation lifecycle targets; migration 0026 adds typed account ban/unban events and a narrowly constrained ban-reason field while preserving earlier rows. Registration uses existing allowlisted email/password/member event kinds and needs no audit schema expansion.
