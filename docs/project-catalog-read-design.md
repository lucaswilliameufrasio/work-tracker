# Project status and issue-type catalogs

Slice228 provides opt-in GET/HEAD `/api/v1/projects/{project_id}/statuses` and `/issue-types` so future issue UI can resolve stored references without guessing localized names or treating operational access as content access. Both use the same session, explicit membership and catalog read snapshot; missing/inaccessible project returns generic404. Archived projects remain readable. No editor, catalog creation/migration, board query or additional membership grant is introduced.

Both catalogs use UUID ascending keyset pages1–100/default50, canonical UUID cursor and `include_archived` default false. UUID order is a stable traversal order, not board display order: statuses carry their existing nonnegative position as a decimal string, preserving SQLite i64 precision. Clients must not assume one page is the complete catalog or silently omit unknown references. Including archived records helps resolve retained issue references; it does not expand project access. Existing unique(project_id,id) indexes cover ordered seeks without a new migration. A later write/reorder between pages need not create a frozen snapshot.

Return IDs, name, optional system_key/archived_at; issue types also expose optional icon_key/color_key as opaque existing tokens (not invented visual definitions), statuses category/position/board_visible. Optional values are omitted. Validate persisted IDs, key grammar, categories, booleans, position and archive timestamp; do not silently normalize corrupt data. Current schema has no maximum name length: row count/lookahead is bounded, not a claim of strict byte/allocation budget or full catalog-edit validation. Future mutations must set product name limits and preserve existing data deliberately rather than invent a read-side cap here.

Tests use migrated SQLite and the real router for pagination, archive inclusion/default exclusion, privacy and session invalidation; EXPLAIN confirms the existing composite indexes. Extend partial OpenAPI and exercise every documented operation. This is prerequisite metadata, not completed Kanban, live-update, login/onboarding or release evidence.
