# Globally ordered board column metadata

Slice234 replaces the read overview's UUID-catalog traversal with GET/HEAD `/api/v1/projects/{project_id}/board`: visible, nonarchived statuses ordered globally by `(position,id)`, page_size1–100/default4, one lookahead and an opaque canonical Base64URL nonnegative-i64-position/UUID cursor. Session identity, explicit membership and metadata share a read transaction. Archived projects remain readable; missing/private projects give generic404. Existing status(project_id,archived_at,position,id) index supports ordering; board_visible is a residual filter, not a claim of constant work or strict SQL deadline.

Only eligible rows are paginated in SQL, so hidden/archived statuses do not create empty candidate pages. Cursor boundary need not survive and grants no access. Future position changes between requests can still repeat/miss rows: this is ordered keyset traversal, not a frozen snapshot. Position is a lossless decimal string. No migration/dependency/editor/reordering operation is added.

The browser overview requests four already-ordered columns and at most20 cards per column. It does not sort a UUID subset, traverse all status catalogs or allocate a whole board. WorkScreen privacy/lifecycle and focused-column pagination remain unchanged. This supersedes slice233's documented local-page ordering limitation, while movement/version/idempotency/outbox/live-update/filtering and other release gates stay open. Tests cover positions out of UUID order, ties, zero/i64MAX, hidden/archive filtering, cursor/privacy, generated contracts and the real browser journey.
