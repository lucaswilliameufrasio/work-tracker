# User email address management — feature design

**Status:** Domain store for pending add, primary selection, listing, and removal implemented. Mutations require an opaque recent-authentication proof: password reauthentication for ordinary users, recent session-bound MFA for installation admins. Confirmation delivery and authenticated routes/UI are not wired.
**Requirements:** `docs/development-plan.md`, sections 7.2 and 7.4.

Addresses are trimmed for display/storage and keyed by outer-trimmed ASCII lowercase; dots and `+tag` remain significant. `add_pending` creates an unconfirmed, non-primary address and rejects any globally reserved comparison key. The existing verification-token store is responsible for confirming it. Only a confirmed address can become primary; selection clears the previous pointer and promotes the target in one `BEGIN IMMEDIATE` transaction.

Removal is owner-scoped and active-account-only. The final stored address and final confirmed address cannot be removed. Removing a primary promotes another confirmed address atomically; a failed delete rolls back that promotion. Deleting an address cascades any pending email-verification and password-reset tokens tied to it. Listing returns only address ID, display address, confirmation time, and primary state.

Adding/removing/changing primary is sensitive. `ReauthenticationService` produces an opaque proof only after checking the current session and password; `MfaStepUpService` resolves the user from the exact live bearer, consumes a newer TOTP step, and rotates that session before producing MFA assurance. The email store rechecks the appropriate exact session marker, active account, and ten-minute freshness inside its own write transaction. Password-only proof remains rejected for installation admins. Both proof types are non-serializable and caller-unconstructible outside the crate. The store does not send verification email, issue login links, mutate invitations, or decide which address receives notifications. Never expose cross-account address existence; `AddressUnavailable` is an internal conflict outcome for generic public handling.
