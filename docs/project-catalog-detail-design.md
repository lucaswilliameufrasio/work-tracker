# Bounded catalog reference resolution

Slice231 adds GET/HEAD `/api/v1/projects/{project_id}/statuses/{record_id}` and `/issue-types/{record_id}`. Each reads one record by the existing unique(project_id,id) index, including archived records still referenced by issues, with bearer identity/project membership/selection in one transaction. Organization authority alone grants nothing. Missing or foreign record/project produces generic404. IDs are canonical UUID selectors; no cursor/archive query options or mutations are accepted. Reuse collection DTOs and persisted-data validation.

The issue detail journey first reads its record, then concurrently reads its journal and the two referenced catalog records, all within the existing eight-second whole-view deadline. Each server transaction authorizes current access independently; there is still no cross-request atomic snapshot. Read failure closes the view rather than guessing a name or silently traversing every catalog page. This replaces the partial first100 metadata strategy for detail, not the catalog collection endpoints or their explicit pagination contract.

Typed clients verify record ID and project match the requested selectors, including archive timestamps. One-row selection bounds row count, not a universal byte budget: current catalog names remain uncapped in SQLite and the browser transport still has512KiB. Tests must place the referenced records beyond100 entries, prove resolution and archive inclusion without traversal, deny private/foreign selectors, update OpenAPI operation coverage, and rerun the complete browser journey and quality gate. No catalog editing, board/mutations, Markdown renderer or onboarding/release approval is implied.
