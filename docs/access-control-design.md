# Authorization policy matrix — feature design

**Status:** The deny-by-default Rust capability policy, fresh SQLite loading of current organization/project access context, transactional project creation, internal project-membership list/add/change/remove/self-leave commands, organization role changes, owner transfer, organization-member removal/self-exit, and internal organization invitation issue/list/cancel/accept commands are implemented. Session-to-principal wiring, HTTP/MCP/job/download/SSE enforcement, audit browsing, and route integration are not implemented.

**Requirements:** `docs/development-plan.md`, sections 5, 6, and 13.

## Actor context and policy

Every decision uses the account state, installation-admin flag, current organization role, current project role, project archived state, and whether a recent privileged-action proof (password reauthentication or MFA step-up) has been verified. Inactive accounts are denied before role checks. Invalid membership combinations fail during context construction: project membership requires organization membership; a guest cannot be project manager or installation admin; installation admins must be organization members.

`AccessStore::load_organization_context` performs one fresh SQLite query joining account state, organization membership, and the separate installation-admin table. It returns `None` for an unknown account, strictly parses persisted state/role values, and fails closed for malformed values or broken admin-membership invariants. It deliberately supplies no project role; the separate project-context loader joins explicit `projects`/`project_members` state. `ProjectStore::create`, `ProjectMembershipStore`, and `OrganizationMembershipStore` use transaction-scoped context loaders while holding SQLite's writer lock. Callers must pass a user ID from a session they have already validated; stores neither authenticate arbitrary IDs nor cache the result. The recent-proof boolean on access loaders remains a trusted caller assertion, not proof validation.

`AccessStore::load_project_context` joins the requested project with the authenticated user's current account state, organization role, installation-admin membership, and explicit project role, plus the project's archived state. It must not grant content access from owner/admin or installation-admin status; an owner/admin context without project membership exists only to authorize the separately defined membership/archive operations and read the participant roster. A caller without project membership or org-admin authority receives `None`, indistinguishable from an unknown project at the transport boundary. Every lookup is fresh; protected operations use transaction-scoped loading so role/archive changes cannot race authorization. Callers still decide a specific capability with `authorize` before touching content.

The `AccessCapability` matrix expresses the policy table without treating roles as content access by themselves:

- Installation-admin capabilities are operational health, installation settings (auth/email/CAPTCHA/backup), and user ban. Full-backup download requires recent password reauthentication or MFA step-up. Installation-admin status alone does not grant project access.
- Organization owners/admins can manage organization membership, create projects, manage project membership, and archive/unarchive projects; only the owner can transfer ownership. Active non-guest organization members may read the names/roles in the organization directory; only owners/admins see confirmed primary emails. Those org roles do not grant project content access.
- Project managers can read/write/manage schema and membership, see participant emails for management, export, and archive/unarchive only their project. Members/viewers (including guests) can read the participant names and roles but not emails. Organization owners/admins can read the roster and emails for management without gaining project-content access. `ProjectMembershipStore` restricts manager assignment to org owner/admin and enforces the guest cap.
- Archived projects permit reads (including the participant roster) and manager exports; organization owners/admins and project managers can archive/unarchive without gaining content access. Ordinary mutations and schema/membership administration are denied until reopened.

## Boundary and remaining work

### Project membership mutations

`ProjectMembershipStore` changes membership only for users already in the organization; invitations and organization membership creation remain separate. Each command opens `BEGIN IMMEDIATE`, reloads the actor's current account/org/project state, checks `ManageProjectMembership`, and revalidates the target's account and organization membership before writing. The caller must supply the actor ID from a validated session; these services do not authenticate arbitrary IDs.

`ProjectMembershipStore::leave` is separate from administrator removal: any active user with explicit membership can remove only their own membership, preserving their organization account (including a guest leaving their last project). It uses the `LeaveProject` capability, which is denied for archived projects; the last manager must appoint a replacement first. The self-leave audit records the same user as actor and subject, and audit failure rolls back the exit.

`ProjectMembershipStore::list` reloads current context and reads the roster in one SQLite read snapshot under `ReadProjectMembership`. Any explicit project member, including a guest/viewer, sees participant IDs, display names, and project roles. Only a project manager or organization owner/admin receives confirmed primary email addresses; pending/non-primary addresses are never returned. Organization owners/admins can use this scoped roster without an explicit project membership, but installation-admin status and ordinary organization membership do not grant it. Roster reads remain available for archived projects; inactive accounts cannot read them.

`OrganizationDirectoryStore::list` reloads current account/organization roles and lists members in one SQLite read snapshot under `ReadOrganizationDirectory`. Active owners/admins/members see organization member IDs, display names, and roles; guests and unaffiliated users do not see the directory. Only owner/admin callers receive confirmed primary email addresses, regardless of installation-admin status. Reads do not create audit events. The query is an internal domain service only; transport/session integration and a bounded pagination contract remain open.

Approved organization-mutation semantics: ordinary role changes may assign only `admin`/`member`/`guest`, and only active existing members may be elevated; owner assignment uses a separate transfer operation. Transfer is an atomic replacement: the new owner must be active, non-guest, and already in the organization; the current owner becomes admin. The independent installation-admin grant is unchanged. Removing an organization member also removes their project memberships in the same transaction, but is refused if any affected project would have no manager. Organization removal never silently changes an installation-admin grant; a separate authorized installation-admin change must happen first. Role changes/removals and each project-membership removal require atomic audit records.

`OrganizationMembershipStore::set_role`, `transfer_ownership`, and `remove` implement these decisions internally. Every mutation starts with `BEGIN IMMEDIATE`, reloads the active actor and target state, and checks the applicable organization capability in that transaction. Ordinary edits cannot assign or demote an owner; owner transfer records the old owner's `owner → admin` and target's `previous → owner` transitions atomically. A guest role requires at least one project membership, cannot retain manager status, and cannot be assigned while the target has an installation-admin grant. Removal rejects owners and installation admins, preflights every project manager count before deleting anything, removes/audits each project membership, then removes/audits the organization membership. Any database or audit error rolls the whole operation back. Disabled accounts may be demoted or removed but cannot be elevated or become owner.

`OrganizationMembershipStore::leave` permits an active organization member to remove only their own membership. It uses the same project-cleanup and audit transaction as administrative removal; audit actor and subject are therefore the leaving user. Owners must transfer ownership first, installation-admin grants must be changed in their separate workflow, and every affected project must retain a manager. Concurrent departures serialize under `BEGIN IMMEDIATE`, so only a departure that leaves another manager can commit.

`OrganizationInvitationStore` manages the internal invitation lifecycle. Owners/admins may invite organization members or guests and assign project roles; project managers may invite only guests into projects where their current manager role is revalidated, with no manager role granted. Every guest invite requires at least one project and cannot contain a manager assignment. Reissuing an email atomically cancels prior unresolved invitations and creates a fresh token; canceled/accepted/expired/pending list states are derived from immutable invitation data and lifecycle timestamps. The default policy is enabled with a seven-day lifetime, while callers can supply the installation's enabled/lifetime settings.

Invitation tokens contain 256 bits of randomness, use invitation-specific digest domain separation, and are returned only by issuance; SQLite stores only the digest. Acceptance requires the current active account, its live recently reauthenticated session, and a confirmed email matching the invitation. Acceptance atomically consumes the invitation, adds organization and project memberships, and writes typed audit events. A project archived after issuance prevents acceptance without consuming the invite. Rejected operations and audit failures leave the invitation and memberships unchanged. This internal service does not create user accounts, deliver email, render/copy invite links, or expose HTTP/MCP/UI routes; those flows must preserve the same checks and keep public identity/session wiring closed until their security boundaries are implemented.

Organization owners/admins may assign any project role and are the only actors who may add, demote, or remove a project manager. A user acting only with project-manager authority may add, change, or remove member/viewer roles but cannot appoint or alter manager membership; an owner/admin who is also a project manager retains the stronger organization authority. Organization guests may hold only member/viewer project roles. New membership and role escalation require an active account; a banned/disabled member may still be demoted, while removal remains available to authorized membership managers. An unchanged role is a no-op with no audit event.

Voluntary demotion/removal cannot leave a project without a manager; promote a replacement first. SQLite triggers enforce this invariant for direct role updates/deletes as well as service calls. Ban does not delete membership. The plan requires a project with no active manager to become read-only; ban workflow and that project-wide read-only enforcement remain unimplemented.

Every committed project-membership add/change/remove is audited atomically with the project as target, the affected user as `subject_user_id`, and typed before/after project roles. Organization membership additions/role changes/removals/self-exit, both sides of ownership transfer, and all project-membership changes caused by those operations are likewise audited with typed organization/project role columns. Invitation creation/reissue/cancel/accept events target an opaque invite ID and contain neither its email nor token. Audit rows do not contain arbitrary payloads; audit failure rolls back the protected changes. Project, organization, and invitation-list reads do not create audit rows. Audit browsing remains unimplemented.

The policy and stores are not yet a general authorization boundary: project creation, project-membership mutations, organization role changes, ownership transfer/removal/self-exit, and invitation issue/cancel/accept recheck current context transactionally; organization/project/invitation read services use transaction-scoped snapshots. No endpoint, job, or project-content use case is wired to them. Public invite delivery/registration, invite/account mode configuration wiring, ban flows, last-manager-ban read-only behavior, principal/session wiring, and remaining protected operations still need implementation. Protected operations must use transaction-scoped loading/fencing and explicit capability checks. Do not cache long-lived claims or use frontend checks as authorization.
