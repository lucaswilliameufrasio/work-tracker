# ADR 0002: Backup archive format selection is deferred

- **Status:** Deferred — security and product compatibility evidence required
- **Date:** 2026-10-06
- **Context:** `docs/development-plan.md`, backup sections 12.2–12.3 and Phase 0 evidence 6–8, 45–46, 49, 51–53, 56–57, 60–62, 69–70, 79–113

## Context

Puxiri backups must remain self-hosted and usable in the single Rust binary. A full bundle must stream the SQLite snapshot and pinned remote files, compress/encrypt with bounded memory, restore into an isolated staging area, and support an offline recovery kit. Production must not require a Node runtime or an external archiver process. Paths, archive entry types/sizes, checksums, publication, interruption recovery and key custody are part of the format boundary.

The existing complete-bundle tests are a Node Phase 0 harness, not production code. A separate Rust scratch spike combined `tar` 0.4.44, `flate2` 1.1.9 with the pure-Rust backend, and `age` 0.12.1 streaming APIs. It encrypted/decrypted 128 MiB of synthetic data under a 1 CPU/1 GiB cgroup, verified the payload, and rejected a wrong identity and modified ciphertext. A follow-up used the Go `filippo.io/age` v1.3.2 reference CLI: Go decrypted and validated the Rust-produced 128 MiB TAR+Gzip stream, while Rust decrypted a short Go-produced ciphertext. This establishes stream-level v1 interoperability for these fixtures, not a Puxiri archive round-trip. The `age` crate explicitly remains beta before 1.0; neither implementation was tested with Puxiri snapshots, S3 pins, restoration policy or recovery keys.

## Decision

The user requires a stable, mature format and dependency API; pre-1.0/beta encryption libraries are not acceptable for selection. Do not select a production archive format or add `age`, `tar`, or compression/encryption dependencies to the product yet. Keep the current Node bundle harness experimental and retain all backup/restore requirements. Do not implement a custom general-purpose encryption/container protocol as a shortcut around the candidate's maturity status.

The Rust `age` crate is excluded under the user's stability criterion. Sequoia OpenPGP 2.4.1/RFC 9580 is a possible *encryption-layer* research lead, not an approved backup candidate: its versioned 2.x crate has documented streaming serializer and decryptor APIs for the IETF OpenPGP message format, but does not define Puxiri's archive manifest, SQLite/S3-pin transaction, staging or publication. Its current published status page (dated 2024-10-02) says it had not been audited at that time; this is stale evidence, not proof of current audit state, and no later independent audit was established here. CVE-2026-42784 describes key-flag confusion/signature forgery; Debian tracks upstream fix commit `58214b47…` in 2.3.0, before current 2.4.1, but an advisory does not establish an independent audit. Default crypto-nettle uses native Nettle; alternative native backends have distinct deployment burdens, while Sequoia says RustCrypto does not yet provide the same security guarantees as mature crypto backends. The crate is LGPL-2.0-or-later; distribution obligations need review. No format or encryption dependency is selected. Any candidate must prove build/distribution compatibility, a narrowly allowlisted modern authenticated-encryption profile, recovery-key import/export, secure allowlisted restoration, full SQLite snapshot plus pinned-object round-trip, crash/disk-full behavior, atomic publication and cgroup resource bounds before selection.

The user explicitly confirms that Puxiri will **not lower its security level to obtain GnuPG compatibility**. Compatibility findings are useful evidence and GnuPG may be an optional independent recovery tool, but whether it is a product requirement remains unconfirmed. Do not adopt legacy/less-protective key or message profiles as a workaround; any profile change needs explicit security review and user approval.

rPGP/`pgp` 0.21.0 is also research-only under the current stability criterion: it is pre-1.0, and its own implementation status says the high-level API is not started. Slices 86–90 do not override the user's maturity requirement. Reconsider only if the user revises that criterion or a later release provides an acceptable stable API and the remaining compatibility/security gates pass.

## Consequences

- No production backup format, endpoint, migration or restore flow is approved by this ADR.
- The Rust age/TAR result is feasibility evidence, not production security approval or a capacity claim.
- Age v1 stream interoperability with the Go reference implementation is verified only for the synthetic fixtures recorded in evidence 49; this does not approve the beta Rust crate or complete bundle format.
- Evidence 51 measures one synthetic Rust archive/snapshot/object composition and isolated restore on tmpfs and local Btrfs; it does not exercise the Puxiri pin/S3 protocol, production manifest or failure contracts, and is not a format selection or capacity claim.
- Evidence 52 rejects a wrong identity and a modified final ciphertext byte in that scratch archive; it does not approve the Rust crate or product publication/recovery behavior.
- Evidence 53 uploads/downloads the synthetic archive with an explicit checksum to disposable local MinIO and restores the downloaded bytes; it does not test presigned/browser flow, S3-provider compatibility, Puxiri pins, or a production manifest.
- Evidence 56 rejects a one-byte-truncated completed archive when the Rust age stream is drained; this is not a matrix of truncation points or product staging/crash behavior.
- Evidence 57 rejects one authenticated relative traversal path before opening an extracted file; it is a scratch allowlist probe, not a complete archive-path security review or product staging implementation.
- Evidence 60 rejects a duplicate path in an authenticated scratch archive. Evidence 61 adds process-level staging cleanup after the tested path-traversal and duplicate-path rejections, with a regression that first failed against the scratch implementation before the guard was added. These do not establish cleanup after process death, resistance to local path races, or product restore safety.
- Evidence 62 records the user's stable-only criterion and a source-level Sequoia review. This is candidate triage only; Sequoia is not audited per its published status page, and no archive or cryptographic profile is selected.
- Evidence 69 compares CMS/OpenSSL, libsodium secretstream, libarchive2 and TAR. No candidate meets the complete stable, audited, bounded-memory, self-hosted and recovery-kit requirements. The prior external scratch TAR pin 0.4.44 was upgraded to patched 0.4.46 after RustSec advisories CVE-2026-33055/33056; the scratch's custom extractor did not call the specifically vulnerable `unpack_in` helper, but the old parser version still fell below the upstream fix floor. The isolated 0.4.46 round-trip/security-fixture run passes; this is not a product dependency approval.
- CMS is a mature standards-track format but the documented Rust `openssl` 0.10.81 wrapper encrypts from a byte slice and decrypts into a `Vec`; OpenSSL documents that its CMS BIO API has streaming encoding but no corresponding inverse streaming decoder. A custom low-level bridge would add unsafe/native integration and patched-runtime obligations; CVE-2026-34182 affected OpenSSL CMS AuthEnvelopedData in supported branches until their fixed releases. CMS therefore remains a research lead, not a selected backup format.
- Libsodium's C `secretstream` API is established (introduced in 1.0.14) and streaming/AEAD, but it is a primitive/wire stream rather than the complete backup/archive and recovery-key format. `libsodium-rs` 0.2.4 is a recent Rust wrapper and requires assessment of its native libsodium build/distribution path; no Puxiri framing or key-kit profile is approved. `libarchive2` 0.2.1 binds mature libarchive but is a young Rust binding and introduces system-library/build and broad-format attack-surface questions.
- Evidence 114 refines the libsodium lead using `libsodium-rs` 0.2.5 (published 2026-09-25; Rust 1.88) and `libsodium-sys-stable` 1.24.0 metadata/docs. Upstream secretstream's XChaCha20-Poly1305 API (available since libsodium 1.0.14) authenticates each bounded message, detects removal/reordering/modification, and requires a final tag; this is a promising streaming primitive. A 32-byte randomly generated data-encryption key could in principle be wrapped to an offline X25519 recovery public key with libsodium sealed-box API, whose operation is one-message rather than streaming. The two APIs still do not define a backup format: Puxiri would need a versioned header, recipient/key envelope, bounded chunk framing/lengths, final-EOF/trailing-byte rules, manifest binding, key import/export, and atomic staged restore. This is a narrow application protocol proposal, not a standard interoperable container; it would need explicit product/security review rather than treating primitives as a format. The published Rust wrapper is recent, and its README's system-install guidance is at odds with `libsodium-sys-stable`'s documented source-build fallback; source-build/static single-binary feasibility and supported target/patch policy must be verified in an isolated build before even a candidate decision. GnuPG/OpenPGP interoperability is not provided by this design. No dependency or product code was changed and no format is selected.
- Evidence 115 runs an isolated Rust spike against `libsodium-sys-stable` 1.24.0, whose generated binding identifies libsodium 1.0.22. With `SODIUM_LIB_DIR`/pkg-config overrides unset, its build script built and linked `static=sodium` from its packaged source; release executable inspection (`ldd` and ELF `NEEDED`) showed no `libsodium.so`, only the normal glibc/loader/`libgcc_s` runtime. Four tests passed: X25519 sealed-DEK recovery plus `secretstream` round trips across empty/short/exact-chunk/multi-chunk boundaries; wrong recovery key, ciphertext tamper, truncation at header/frame/final-frame offsets, trailing bytes, oversized length, altered header and altered authenticated length were rejected; a synthetic 128 MiB `Read`→file→`Read` stream restored through fixed-size 64 KiB frames and a checking `Write` sink without the API collecting the stream. `cargo fmt`, release tests, Clippy `-D warnings`, and release build passed. This demonstrates one-host native static-link feasibility and API-level bounded streaming, not a fully static executable, cross-target/reproducible/offline build, reviewed Rust unsafe boundary, memory cgroup benchmark, recovery-key export/protection/import, compression, authenticated production manifest, Puxiri SQLite/pinned objects, path extraction, or crash-safe staging. The spike's custom framing writes earlier authenticated plaintext to its caller-provided writer before final tag/EOF validation; production restore must target private staging and publish only after the entire authenticated stream and inventory validate. No code/dependency entered the product; format remains unselected.
- Evidence 116 extends the isolated spike with a portable recovery-key kit and a distinct restore subprocess. The fixture file is 129 bytes: magic/version, fixed profile id, X25519 public key, random 16-byte salt, random 24-byte XChaCha20-Poly1305 nonce and authenticated encrypted 32-byte private key. Argon2id uses libsodium's named MODERATE constants (opslimit 3, memlimit 268,435,456 bytes) with fixed profile id; no attacker-controlled KDF costs are decoded. Magic/version, exact file size, profile and passphrase length (12–1,024 bytes) are checked before KDF. All header/profile/salt/nonce/public-key bytes are AEAD associated data. Passphrase arrives via bounded stdin, key material uses `sodium_memzero` guards, and newly created kit/output files request Unix mode 0600. One process generated kit+bundle; a new process read the protected kit and restored the bundle. Wrong passphrase and corrupted kit failed before output creation; corrupted bundle failed and scratch output was removed. Four unit tests plus this integration test passed; fmt, Clippy `-D warnings`, release build passed. Repeating the subprocess integration test under a verified cgroup (`memory.max=1,073,741,824`, `cpu.max=100000 100000`) peaked at 284,405,760 bytes for this entire sequential test run. This is not a production profile selection, password-entropy/normalization UX decision, concurrent KDF bound, cross-host/architecture recovery test, crash-durable kit writer, or app-under-load capacity benchmark; concurrent restores can multiply KDF memory. Bundle/kit wire formats remain synthetic and unaudited, and no product code/dependency was changed.
- Evidence 117 composes and restores a synthetic full bundle only in the external scratch. It uses `rusqlite` 0.39.0's SQLite Online Backup API for a read-only database snapshot, accepts only regular pinned-object fixture files whose lowercase hex IDs are 64 characters, writes a versioned inventory (entry count/type/path/size/BLAKE2b-256) through Gzip and the existing libsodium secretstream, and restores through a fresh Unix 0700 staging directory. Restore bounds the decrypted compressed spool to 2 GiB + 64 MiB, entries to 4,097, each entry to 512 MiB and aggregate file bytes to 2 GiB; it allows only `database.sqlite` and `objects/<64 lowercase hex>`, rejects links/traversal/duplicate paths and validates byte count/hash, SQLite integrity, manifest EOF, Gzip CRC/EOF and compressed/plaintext trailing bytes before returning success. Subprocess fixture created a kit, composed a synthetic SQLite database plus two objects, then another process restored and read back the database row and exact object bytes. Negative tests rejected traversal, duplicate, non-regular type, bad hash, truncated gzip, trailing compressed/decompressed data and modified ciphertext; returned errors left no staging directory. Seven unit and one integration test passed; fmt check, Clippy `-D warnings`, release tests and build passed offline. Two subprocess integration scopes ran under verified `memory.max=1,073,741,824` and `cpu.max=100000 100000`, with `memory.peak` 452,292,608 and 457,191,424 bytes; these include Cargo/test/runtime and sequential Argon2 KDF processes, and are not per-operation/concurrent/representative capacity measurements. This does not test live-write concurrency within the scratch composer (separate Phase 0 snapshot test covers the API), full-scale inputs, authenticated production metadata/pin protocol, checksum against adversarial concurrent source mutation, ENOSPC, interruption/SIGKILL/power loss, cleanup after death, retention, path-race defense, directory durability/atomic publication, cross-platform packaging or independent review. Bundle and recovery kit remain proprietary synthetic formats, no product code/dependency was changed, and ADR selection remains deferred.
- Evidence 118 adds two failure probes to that isolated scratch. A valid encrypted bundle restored through an intentionally one-byte compressed-spool limit fails before archive extraction and removes stage; this checks configured quota/error cleanup, not a true filesystem ENOSPC or device failure. A test-only subprocess pause after the first staged SQLite file is synced creates a marker; the integration test sends SIGKILL (signal 9), verifies the stage directory still exists privately with the database but without not-yet-extracted objects, and cleans it only through the test's enclosing temporary-directory teardown. This demonstrates the known abrupt-death residue and does not claim recovery, auto-cleanup or publication safety if a caller misuses stage. Eight unit plus one integration test passed; fmt check, Clippy `-D warnings`, release tests/build passed offline. The subprocess run under verified cgroup (`memory.max=1,073,741,824`, `cpu.max=100000 100000`) peaked at 433,991,680 bytes including Cargo/runtime/KDF children, not an isolated or concurrent workload measurement. No product code/dependency or real data was used. True filesystem ENOSPC/partial-write, interruption during composition/publication, recovery/cleanup after death, directory fsync and atomic durable rename remain untested; no candidate is selected.
- Evidence 119 injects a real `io::ErrorKind::StorageFull` from Linux `/dev/full` into the encrypted-compressed-spool writer during restoration. The ENOSPC propagates through the decrypt path and the newly created stage directory is removed; the probe does not fill a filesystem, validate quota accounting, or produce a partial successful write. This complements (but is distinct from) the configured one-byte spool cap and SIGKILL residue probe. Nine unit plus one subprocess integration test passed; fmt check, Clippy `-D warnings`, offline release tests/build passed. No product code/dependency or real data was changed/used. Filesystem/quota exhaustion, mid-frame partial write, crash during composition/publication, recovery cleanup and durable atomic publication remain open; the format remains deferred.
- Evidence 70 identifies Restic's repository format as a stronger mature-format lead: Restic 0.19.1 is actively released, documents repository format v2, append-only objects, pack/index/snapshot ordering, and password-protected multiple keys. However, this is a multi-object repository protocol, not the single self-contained encrypted bundle defined in section 12.2. The Rust library `rustic_core` 0.13.0 reads/writes that format and offers backup/restore APIs under Apache-2.0/MIT, but its own crate documentation explicitly calls the API early-stage and subject to change; it does not meet the user's stable dependency-API bar today. Using the mature Go `restic` binary as a subprocess would violate the single-binary/no-external-archiver constraint. No candidate is approved.
- Restic's documented data encryption is AES-256-CTR plus Poly1305-AES, with keys protected by password-derived key files; this is established implementation practice but is not an IETF-standardized AEAD profile. The exact cryptographic profile, implementation review, key-recovery workflow and whether a repository protocol can replace the plan's self-contained full bundle require explicit security/product review. Repository integrity/order properties do not by themselves prove Puxiri's SQLite snapshot, S3-pin, staging, publication, retention or crash contracts.
- Evidence 79 updates the Sequoia lead: crate 2.4.1 documents streaming serialize/decrypt APIs over RFC 9580, a stable IETF message standard, but is only an encryption-envelope possibility. Sequoia's low-level crate explicitly avoids choosing downstream trust/use policy; its published status page says “not audited yet” as of 2024-10-02 (current audit status not established). The CVE-2026-42784 key-flag/signature issue is tracked by Debian as fixed upstream in 2.3.0; 2.4.1 postdates that tag, but this says nothing about independent audit or future advisories. Default Nettle/native build, non-recommended RustCrypto security guarantees, LGPL-2.0-or-later obligations, and passphrase/recovery policy remain unresolved. No complete archive or cryptographic profile is approved.
- Evidence 80 compiles an isolated API smoke only after opting into Sequoia's `crypto-rust`, `allow-experimental-crypto`, and `allow-variable-time-crypto` flags. A synthetic 8 MiB file round-trips through the stream writer/reader with AES-256 + OCB, wrong passphrase and a damaged final byte fail, and the scratch wrapper withholds rename/publication on failure. The default Nettle backend did not build because this host lacks the Nettle development header `nettle/pgp.h`; no system package was installed. Because the only successful run used a backend Sequoia explicitly calls experimental and variable-time, this is API/stream composition evidence only—not cryptographic, security, performance, memory-bound, interoperability, or production suitability evidence. The simple scratch rename also lacks production durability/hostile-path guarantees. Sequoia remains unselected.
- Evidence 81 repeats the same synthetic 8 MiB stream/tamper smoke using Sequoia's documented `crypto-openssl` backend against system OpenSSL 3.6.4; locked offline fmt, Clippy `-D warnings`, all-target tests and release build pass. The produced test binary dynamically links `libssl.so.3` and `libcrypto.so.3`, so this is not evidence for a self-contained single-binary distribution. It removes the need for the experimental RustCrypto flags on this host, but does not establish cryptographic profile safety, OpenPGP interoperability, independent audit status, supported deployment matrix, LGPL distribution compliance, memory/cgroup bounds or complete backup suitability. Backend remains unselected.
- Evidence 82 attempts external interoperability with the locally installed GnuPG 2.4.9/libgcrypt 1.12.3, without lowering Sequoia's `StandardPolicy`: GnuPG rejects Sequoia output's version-6 SKESK as unknown; Sequoia rejects GnuPG's forced-AEAD output because it is AEAD Encrypted Data Packet v0, which the current policy considers insecure. Both sides fail closed and staging is withheld. This is a real compatibility gap for these exact local versions/configuration, not proof of general RFC 9580 incompatibility or behavior in newer GnuPG; no bidirectional interoperable backup profile was established. A future candidate needs independent-tool interoperability with current supported versions and an explicitly reviewed compatibility policy.
- Evidence 83 proves bidirectional synthetic stream compatibility between Sequoia 2.4.1 (`crypto-openssl`) and OpenPGP.js 6.3.1 on Node 24.21.0 when both explicitly use RFC 9580 AEAD OCB/AES-256: OpenPGP.js decrypts Sequoia output and Sequoia decrypts OpenPGP.js output under their standard policy/default S2K choices. This is a single 8 MiB fixture and does not establish interoperability with GnuPG, archival profile suitability, external audit, passphrase/KDF strength, complete bundle semantics, or production security. OpenPGP.js is a distinct implementation, but its AEAD path is behind an explicit opt-in and its LGPL-3.0 license is an additional test-only/tooling fact, not a product choice. No JS package or Rust crate was added to the checkout.
- Evidence 84 reviews actual passphrase-S2K defaults and verifies the interoperable Argon2 option in a one-way synthetic fixture. Sequoia 2.4.1's `S2K::default()` uses salted+iterated SHA-256 at the maximum representable count `0x3e00000` (65,011,712 input bytes, about 62 MiB of hashing; not memory-hard). OpenPGP.js 6.3.1 defaults to iterated S2K coded count byte 224 (16 MiB of hashing; also not memory-hard), but supports RFC 9580 Argon2 S2K when explicitly selected; its documented defaults are `t=3,p=4,m=2^16 KiB` (64 MiB RAM). With those defaults, OpenPGP.js encrypted an 8 MiB synthetic stream and Sequoia decrypted it successfully. RFC 9580 recommends Argon2 and permits iterated+salted S2K when Argon2 is unavailable with a high count and strong passphrase. This does not select Argon2 params for Puxiri, assess entropy/UX or concurrent memory/DoS bounds, test recovery over time, or establish GnuPG compatibility for this exact packet profile.
- Evidence 85 inspects the official GnuPG 2.5.24 source tarball, the current stable release listed on gnupg.org on 2026-10-06, without building or executing it. `g10/parse-packet.c::parse_symkeyenc` accepts SKESK versions 4 and 5 only and S2K modes 0, 1, and 3 only; version 6 and Argon2 mode 4 are rejected by source control flow. This independently corroborates the local GnuPG 2.4.9 fixture gap and shows that RFC9580 v6 SKESK/Argon2 interoperability cannot be claimed for the current official GnuPG stable source. It is a source inspection, not a runtime test, and says nothing about other OpenPGP clients or future GnuPG changes. The upstream tarball was fetched over HTTPS; no system software was installed and no user data/keys were used.
- Evidence 86 evaluates rPGP 0.21.0 (MIT OR Apache-2.0, pure Rust) as a second RFC 9580 envelope implementation. Its low-level API has `Read`/`Write` message paths and supports SKESK v6, SEIPDv2 OCB and Argon2 S2K; its own implementation status says the high-level API is not started. An isolated 8 MiB file-streaming harness using Argon2id `t=3,p=4,m=64 MiB`, AES-256/OCB passed bidirectionally with OpenPGP.js 6.3.1 using the same S2K/AEAD profile. Tampering with the last byte made decrypt return an authentication error, but 8,110,080 plaintext bytes had already reached the harness output file before final-tag verification. Any caller must write exclusively to private staging and publish only after complete EOF and success; this test is not atomic restore behavior. Source inspection shows an Argon2 parser cap of 2 GiB per derivation and `t,p<=32`, which does not establish a safe concurrent-memory bound. The crate reports a 2024 Radically Open Security audit with listed findings fixed, but its current `SECURITY_STATUS.md` also lists an unresolved Marvin/side-channel concern in its RSA dependency; the symmetric password-only test does not exercise RSA. The harness uses no public-key RSA, tests only one client pair/profile, and does not establish GnuPG interoperability (evidence 85's parser limitation still applies), complete bundle semantics, bounded RSS, independent current review, or suitability. No crate or code was added to Puxiri.
- Evidence 87 inspects rPGP 0.21.0's public `Message::Encrypted { esk, .. }`, `Esk::SymKeyEncryptedSessionKey(packet)`, and `packet.s2k()` API: callers can inspect and reject S2K parameters before invoking the convenience `decrypt_with_password`, which derives directly from packet parameters. The crate's own `Message` docs warn plaintext may be arbitrarily large and recommend a limiting reader, but explicitly require treating a read that stops at the limit with unread input as unsuccessful. Therefore a size cap cannot be treated as successful authenticated EOF: caller must reject overflow while still draining/validating the full AEAD stream or keep all output private and discard it. This is a source/API feasibility observation, not a test that a complete safe preflight/limit wrapper has been implemented.
- Evidence 88 exercises the recovery-key path at API level in the isolated rPGP harness: it generated an ephemeral OpenPGP v6 Ed25519 primary plus X25519 encryption subkey, encrypted an 8 MiB synthetic file with PKESK v6/SEIPDv2 OCB/AES-256, decrypted and compared bytes. This demonstrates an in-process RFC 9580 public-key encryption route compatible in concept with the plan's offline private recovery key. It does not serialize/import the private key across processes, test encrypting/protecting the recovery-kit private key, OpenPGP.js/GnuPG interoperability, key rotation/loss, authenticated manifest metadata, cgroup bounds, or the complete archive. The generated key is disposable synthetic material; no product dependency or implementation was added.
- Evidence 89 extends the isolated harness to serialize the generated v6 private recovery key, import it in a separate process, decrypt the synthetic 8 MiB bundle and compare byte-for-byte. The v6 key builder uses its documented default secret-key protection: Argon2id `t=3,p=4,m=64 MiB` and AES-256/OCB. Wrong key passphrase returned `MissingKey` before the harness created an output file. This is a useful kit-portability/API smoke, not a recovery UX, permissions, multi-host, interoperability, rotation/loss or product atomic-publication test; the secret artifact contains only disposable synthetic key material and fixtures.
- Evidence 90 establishes only a version-scoped asymmetric recovery-key interop result. OpenPGP.js 6.3.1 generated an RFC 9580 v6 Curve25519 keypair with Argon2-protected private key; rPGP 0.21.0 parsed/validated that private key and decrypted the OpenPGP.js-encrypted 8 MiB OCB/AES-256 fixture. In the opposite message direction, rPGP encrypted the same fixture to that OpenPGP.js public key and OpenPGP.js decrypted it. However, OpenPGP.js 6.3.1 failed parsing the rPGP-generated v6 Ed25519/X25519 public/private key with `MalformedPacketError: Parsing SignaturePacket failed: Error reading MPIs`, even when `v6Keys: true`. Failure occurs while parsing the key certificate, before unlock or message decryption. This does not identify which implementation diverges or establish all-client behavior; it means we cannot claim rPGP-generated recovery-key portability to OpenPGP.js 6.3.1 without investigating/fixing the discrepancy. All files/keys are synthetic, no GnuPG runtime test or product dependency/change.
- Evidence 91 tests Sequoia 2.4.1 (`crypto-openssl`, `StandardPolicy`) with an OpenPGP.js 6.3.1-generated v6 Curve25519 secret recovery key protected by Argon2. Sequoia parsed/imported the key and decrypted the OpenPGP.js-generated 8 MiB RFC 9580 OCB/AES-256 stream; wrong key passphrase was rejected. In the reverse direction, Sequoia encrypted an 8 MiB stream to that same OpenPGP.js v6 certificate and OpenPGP.js 6.3.1 decrypted it; both bytewise comparisons passed. - Evidence 96 qualifies the static OpenSSL result: crates.io's current `openssl-src` versions list (queried 2026-10-06) has 300.6.1+3.6.3 as the newest 3.x source crate, while the official OpenSSL 3.6.4 security release is dated 2026-08-25. The static scratch therefore embeds 3.6.3, not current 3.6.4; official 3.6.4 release notes enumerate multiple fixes, including CVE-2026-54876 and CVE-2026-63072. No reachability analysis was performed, so do not infer those paths are exploitable through Sequoia; do treat the source lag as a patch-management blocker. `cargo audit` on RustSec snapshot did not report embedded OpenSSL source CVEs. A patched vendored/static build or supported system-OpenSSL dynamic build must be proven before adopting this route. No product dependency change.
- Evidence 97 source-reviews Sequoia 2.4.1 RFC9580 Argon2 S2K handling. Parser accepts byte-sized `m,t,p`; `S2K::derive_key` computes memory as `2u32.checked_pow(m)` KiB and passes parameters to argon2 0.5.3. This rejects exponent `m>31` by overflow but allows a theoretical `m=31` = 2,147,483,648 KiB (~2 TiB); `t,p` values up to 255 are accepted by the wire type and Argon2 crate limits are much higher than application policy. Sequoia's `Blocks::new` uses fallible `alloc_zeroed`, but no bounded per-request/concurrent resource policy is applied there. No high-cost parameters were executed. Public `SKESK::s2k()` exposes content KDF parameters. For encrypted secret keys there is no direct `Key::s2k()` method: callers can inspect `Key::secret()` and match `SecretKeyMaterial::Encrypted(encrypted)`, then read `encrypted.s2k()` before `decrypt_secret`. Applications must strictly allowlist S2K profile/cost and bound concurrency before deriving from untrusted data. This is a source/API review, not a demonstrated exploit or finding against the library, and does not establish OOM behavior of the host allocator. No product change.
- Evidence 98 inspects Sequoia's secret-key protection path used for the v6 recovery-key portability test. `CertBuilder` encrypts generated secret material via `encrypt_in_place`, whose default calls `S2K::default`; for v6 this is iterated SHA-256 at the max representable `0x3e00000` count (~65 MB of hash input, about 62 MiB), not memory-hard Argon2. `SecretKeyMaterial::encrypt_in_place_with` takes an explicit `S2K`, symmetric cipher and optional AEAD, so callers can choose a different protection profile; no Argon2 profile/UX has been selected for Puxiri. This means the key portability test proves passphrase-protected import/export, not approved recovery-key KDF strength. No secret/user data or product changes.
- Evidence 99 exercises that explicit route in isolated scratch. A synthetic Sequoia 2.4.1 RFC 9580 v6 Ed25519/Cv25519 keypair had each secret packet reprotected using explicit Argon2 S2K `t=2,p=1,m=16` (64 MiB), AES-256 and OCB, with fixed test-only salt. OpenPGP.js 6.3.1 parsed the serialized transferable secret key, rejected a wrong passphrase, unlocked it with the fixture passphrase, and decrypted an 8 MiB Sequoia recipient-encrypted stream; Sequoia independently decrypted the stream and both bytewise comparisons passed. This proves API and version-scoped interoperability for this intentionally synthetic low-cost profile, not strength/entropy of chosen parameters, secure salt generation (test salt is fixed), production recovery-kit policy/UX, GnuPG, other clients, or long-term portability. Scratch fmt, Clippy `-D warnings`, all 7 tests, release build passed against system dynamic OpenSSL 3.6.4 using a separate target directory because `/tmp` was full; no product changes or dependencies.
- Evidence 100 directly compiles and exercises Sequoia's preflight access route on that Argon2-protected key: match `key.secret()` as `SecretKeyMaterial::Encrypted(encrypted)` and read `encrypted.s2k()` to assert `Argon2(t=2,p=1,m=16)` before calling `decrypt_secret`. This corrects the convenient but inaccurate `Key::s2k()` shorthand in evidence 97; the direct method does not exist. The focused test passed. This confirms caller inspection is possible, not that it is enforced automatically by Sequoia.
- Evidence 101 reviews OpenPGP.js 6.3.1 Argon2 resource controls. Its configured default output profile is `t=3,p=4,m=16` (64 MiB), but `maxArgon2MemoryExponent` defaults to 30 (=1 TiB) and its explicit check in `Argon2S2K.produceKey` applies to both encrypt/decrypt; it rejects larger `m` before invoking the Argon2 WASM module. Thus the hard-coded default ceiling is vastly larger than the default profile and must be lowered explicitly for untrusted recovery keys. This documented cap only bounds memory exponent; no source evidence found in this review for a corresponding cap on untrusted `t` or `p`, and no extreme parameters were run. This is version-scoped source review, not a vulnerability or suitability claim.
- Evidence 102 runtime-checks that configuration guard without invoking high-cost Argon2: the scratch creates a v6 secret key using S2K `m=16` (64 MiB), then a separate OpenPGP.js 6.3.1 harness sets `maxArgon2MemoryExponent=15` (32 MiB) and tries `decryptKey`. It rejects with wrapped message `Error decrypting private key: Argon2 required memory exceeds config.maxArgon2MemoryExponent`; source order places this guard before Argon2 WASM invocation. The same fixture passes the normal configured cap for decrypt, wrong passphrase is rejected, and Sequoia/OpenPGP.js stream comparisons pass. This verifies the caller-configurable m cap on this version, not t/p caps, concurrent limits, actual process peak RSS, or production policy. Scratch fmt/Clippy/all 7 tests/release build passed on system dynamic OpenSSL 3.6.4; no product code/dependency.
- Evidence 103 replaces fixed test-only salts with a fresh 16-byte salt from Sequoia's documented `crypto::random` CSPRNG separately for the generated v6 primary and encryption subkey. The synthetic protected key remains interoperable with OpenPGP.js 6.3.1 (including cap-preflight, wrong-passphrase rejection and successful stream decryption); the test asserts both salts are present and unequal. This exercises a realistic salt-generation API path, but does not select Argon2 costs/profile, validate entropy/OS RNG failure handling in deployed targets, or approve recovery UX/kit. All scratch fmt, Clippy, 7 tests and release build passed; no product dependency.
- Evidence 104 inspects the bundled OpenPGP.js 6.3.1 Argon2 WASM implementation's memory/lifecycle beyond its configured exponent ceiling. `setupWasm` creates one `WebAssembly.Memory` per loaded module with `maximum: 65536` 64-KiB pages (4 GiB), so many costs allowed by the exponent hard cap (`m` up to 30 = 1 TiB) cannot actually fit and will fail allocation; the module translates known memory-growth errors to `Argon2OutOfMemoryError`. The synchronous `computeHash` call writes/clears the shared WASM memory in one JS realm and cannot overlap with another event-loop callback during its synchronous section; WASM is module-cached. After a completed call with decoded memory > `2<<19` KiB (1 GiB), OpenPGP.js schedules a module reload to enable deallocation. This is implementation-source behavior, not measured RSS/cgroup or a cross-worker/process/global concurrency limit; separate workers/processes have independent instances. Low application cap and deployment-level worker budgeting remain necessary. No high-cost input executed.
- Evidence 105 source-reviews the OpenPGP.js 6.3.1 Argon2 parameter parser/validator for CPU bounds. `Argon2S2K.read` copies wire `t,p,m` bytes; `produceKey` enforces the configured memory exponent only. Bundled `argon2id.validateParams` checks `memorySize >= 8*parallelism` and byte lengths, but no explicit pass/parallelism maximum; the synchronous implementation loops `pass < ctx.passes`. Therefore an input can request up to 255 passes in this wire profile, potentially multiplying CPU work while respecting a low memory cap. No extreme/high-pass input was run. This is code-path/source evidence, not a timing result or vulnerability classification. Treat Argon2 parameters as an exact allowlisted profile before key unlock; memory cap alone is not CPU bound. No product change.
- Evidence 106 extends the scratch preflight harness to inspect OpenPGP.js 6.3.1's parsed private-key packet objects before unlock. For the generated v6 certificate, the primary packet and one subkey both expose `s2k.type`, `t`, `p`, `encodedM`, and `salt`; the harness asserts Argon2 `t=2,p=1,m=16` for both and distinct salts before exercising the configured `m=15` rejection. This demonstrates a version-scoped caller inspection route to implement an exact S2K allowlist without deriving first. It is not a supported stable public-policy API guarantee, and does not bound work in other packet/message paths. Scratch fmt, Clippy `-D warnings`, all seven tests and release build passed; no product code/dependency.
- Evidence 107 exercises the configured OpenPGP.js 6.3.1 memory ceiling on both secret-key decryption and encryption. With `maxArgon2MemoryExponent=15`, decrypting the synthetic Argon2 `m=16` key rejects before WASM derivation. A separate copy is unlocked under normal limits, then `SecretKeyPacket.encrypt` is called with Argon2 output `m=16`, AES-256/OCB, and cap `m=15`; that also rejects with the memory-cap error before derivation. The harness includes AEAD configuration, required by this profile. Exact-profile field inspection, distinct salts, normal unlock/stream interoperability and wrong-passphrase rejection still pass. This is a runtime test of this package/version's input and output cap paths, not a policy selection or global resource bound. Scratch fmt, Clippy `-D warnings`, all seven tests and release build passed; no product code/dependency.
- Evidence 108 mutates only a disposable serialized secret-key S2K pass-count octet from 2 to 255, leaving salt, `p=1`, `m=16`, encrypted secret bytes and packet lengths unchanged. Sequoia 2.4.1 parses the modified transferable certificate and exposes the Argon2 `t=255,p=1,m=16` parameters through `SecretKeyMaterial::Encrypted(...).s2k()` without a derivation attempt. No decrypt/unlock is called on the mutated key, avoiding the deliberately expensive CPU work. The normal unmodified fixture still passes interop. This proves parser-level acceptance plus caller-visible preflight for this packet/version, not cryptographic validity of the modified secret material, exploitability, or resource impact. Scratch fmt, Clippy, all seven tests and release build passed; no product code/dependency.
- Evidence 109 repeats the parse-only mutation independently for the Argon2 parallelism octet: starting from the untouched `t=2,p=1,m=16` synthetic key, set only `p=255`; Sequoia 2.4.1 parses the certificate and exposes `t=2,p=255,m=16` through the encrypted-secret S2K accessor. The mutated key is never unlocked, so no Argon2 allocation/derivation is performed. Together with evidence 108, this demonstrates parser acceptance and preflight visibility of extreme encoded t and p for this version. It does not establish that Argon2 derivation would accept the tuple, that the modified secret material is decryptable, or any exploit/resource impact. Scratch fmt, Clippy, all seven tests and release build passed; no product changes.
- Evidence 110 performs the same parse-only mutation for `m`, changing only the memory-exponent octet from 16 to 31 while retaining `t=2,p=1`. Sequoia 2.4.1 parses the certificate and exposes `Argon2(t=2,p=1,m=31)` before derivation. The fixture is never decrypted; this does not claim a 2-TiB allocation is attempted/succeeds, nor that secret ciphertext is valid. Combined slices 108–110 show that the three one-byte S2K cost fields are parser-visible at extreme encodings, reinforcing the need for an application allowlist before decryption. Scratch fmt, Clippy, all seven tests and release build passed, with no product code/dependency.
- Evidence 111 follows up the GnuPG 2.5.24 source parser lead with an isolated runtime build (official release tarball/revision 66dfde9fd; system libgcrypt 1.12.3 and libassuan 3.0.0; a copied include-only workaround corrected a malformed `#defined` directive in the host libassuan header; no system install). GnuPG rejected importing a Sequoia RFC9580 Ed25519-v6 unprotected synthetic key because it could not verify signature algorithm 27. A Sequoia v6 RSA primary/RSA encryption-subkey unprotected synthetic key imported, but GnuPG's decrypt of its own matching Sequoia AES-256/OCB SEIPDv2 message failed with `cipher algorithm 163 is unknown or disabled`; packet listing showed PKESK v6/RSA and SEIPD-v2/AES-256/OCB, but root cause of the session-key decode failure was not established. A separate RSA-primary/X25519-subkey fixture imported, yet GnuPG listed the subkey invalid and decryption failed `No secret key`. All inputs and keys were generated fixture-only; GPG homes were private scratch directories and agents shut down. This is version/build/profile-specific negative evidence, not proof RFC9580 is generally incompatible; current GnuPG cannot be counted as a validated restore client for these profiles. No candidate/product change.
- Evidence 112 repeats the key/message operations with GnuPG's explicit `--allow-9980` flag, which gates RFC 9980 crypto behavior (the earlier slice111 Ed25519 import failure was default/no flag).
