# ADR 0002: Backup archive format selection is deferred

- **Status:** Deferred — security and product compatibility evidence required
- **Date:** 2026-10-06
- **Compatibility clarification:** 2026-10-18 — the operator confirmed that the Puxiri offline restorer and recovery kit are sufficient; no external recovery tool is mandatory.
- **Evaluation priority:** 2026-10-18 — the operator selected Sequoia/OpenPGP for the next candidate evaluation, not production adoption. See [evaluation gates](../backup-sequoia-evaluation.md).
- **Context:** `docs/development-plan.md`, backup sections 12.2–12.3 and Phase 0 evidence 6–8, 45–46, 49, 51–53, 56–57, 60–62, 69–70, 79–113

## Context

Puxiri backups must remain self-hosted and usable in the single Rust binary. A full bundle must stream the SQLite snapshot and pinned remote files, compress/encrypt with bounded memory, restore into an isolated staging area, and support an offline recovery kit. Production must not require a Node runtime or an external archiver process. Paths, archive entry types/sizes, checksums, publication, interruption recovery and key custody are part of the format boundary.

The existing complete-bundle tests are a Node Phase 0 harness, not production code. A separate Rust scratch spike combined `tar` 0.4.44, `flate2` 1.1.9 with the pure-Rust backend, and `age` 0.12.1 streaming APIs. It encrypted/decrypted 128 MiB of synthetic data under a 1 CPU/1 GiB cgroup, verified the payload, and rejected a wrong identity and modified ciphertext. A follow-up used the Go `filippo.io/age` v1.3.2 reference CLI: Go decrypted and validated the Rust-produced 128 MiB TAR+Gzip stream, while Rust decrypted a short Go-produced ciphertext. This establishes stream-level v1 interoperability for these fixtures, not a Puxiri archive round-trip. The `age` crate explicitly remains beta before 1.0; neither implementation was tested with Puxiri snapshots, S3 pins, restoration policy or recovery keys.

## Decision

The user requires a stable, mature format and dependency API; pre-1.0/beta encryption libraries are not acceptable for selection. Do not select a production archive format or add `age`, `tar`, or compression/encryption dependencies to the product yet. Keep the current Node bundle harness experimental and retain all backup/restore requirements. Do not implement a custom general-purpose encryption/container protocol as a shortcut around the candidate's maturity status.

The Rust `age` crate is excluded under the user's stability criterion. Sequoia OpenPGP 2.4.1/RFC 9580 is a possible *encryption-layer* research lead, not an approved backup candidate: its versioned 2.x crate has documented streaming serializer and decryptor APIs for the IETF OpenPGP message format, but does not define Puxiri's archive manifest, SQLite/S3-pin transaction, staging or publication. Its current published status page (dated 2024-10-02) says it had not been audited at that time; this is stale evidence, not proof of current audit state, and no later independent audit was established here. CVE-2026-42784 describes key-flag confusion/signature forgery; Debian tracks upstream fix commit `58214b47…` in 2.3.0, before current 2.4.1, but an advisory does not establish an independent audit. Default crypto-nettle uses native Nettle; alternative native backends have distinct deployment burdens, while Sequoia says RustCrypto does not yet provide the same security guarantees as mature crypto backends. The crate is LGPL-2.0-or-later; distribution obligations need review. No format or encryption dependency is selected. Any candidate must prove build/distribution compatibility, a narrowly allowlisted modern authenticated-encryption profile, recovery-key import/export, secure allowlisted restoration, full SQLite snapshot plus pinned-object round-trip, crash/disk-full behavior, atomic publication and cgroup resource bounds before selection.

The user explicitly confirms that Puxiri will **not lower its security level to obtain GnuPG compatibility**. On 2026-10-18, the operator selected **“Puxiri offline basta”**: the Puxiri offline restorer and recovery kit are sufficient; GnuPG or any other external recovery tool is **not a mandatory product requirement**. External interoperability findings remain useful optional evidence, but failure to interoperate with GnuPG alone does not disqualify an otherwise acceptable candidate. Do not adopt legacy/less-protective key or message profiles as a workaround; any profile change needs explicit security review and user approval. This clarification does not approve a format, library, cryptographic profile, dependency addition, or custom container protocol, and does not relax the stable/mature API or security gates above.

rPGP/`pgp` 0.21.0 is also research-only under the current stability criterion: it is pre-1.0, and its own implementation status says the high-level API is not started. Slices 86–90 do not override the user's maturity requirement. Reconsider only if the user revises that criterion or a later release provides an acceptable stable API and the remaining compatibility/security gates pass.

On 2026-10-18, the user authorized **prioritizing Sequoia/OpenPGP evaluation**. This narrows the research order; it does not select a production dependency, backend, key profile or archive format. Registry/docs now list Sequoia 2.4.2 (published 2026-10-14), whereas the existing runtime evidence above is for 2.4.1. Do not transfer the old test results to 2.4.2 without rerunning them. The current documentation, security and distribution gaps are tracked in [the evaluation note](../backup-sequoia-evaluation.md); this ADR remains Deferred.

On 2026-10-19, evidence 217 reconciled the published 2.4.1/2.4.2 package diff and ran the unmodified upstream key/encrypt/decrypt example with **Sequoia 2.4.2 plus statically linked OpenSSL 3.5.9 LTS**, built from checksum/signature-verified official source in an isolated scratch. The small smoke also passed in a rootless no-network/read-only container with only the binary mounted, and a scratch-lockfile RustSec scan reported zero known vulnerabilities. This is a one-host feasibility result, not a full-stream/profile/backup/security/portability or licensing approval; OpenSSL's own tests were not run, and native code is outside that Cargo audit scan. Details, hashes and limits are in the evaluation note. The old 2.4.1 robustness tests have not been rerun against 2.4.2. ADR status stays Deferred.

## Consequences

- No production backup format, endpoint, migration or restore flow is approved by this ADR.
- The required recovery acceptance path is Puxiri offline restore using the bundle and recovery kit. Its distribution/version compatibility, documented offline procedure, key import/export, full restore and failure/security evidence remain required. GnuPG compatibility is optional, not a release gate. Format selection remains Deferred until the other acceptance criteria are met.

- Evidence 69 compares CMS/OpenSSL, libsodium secretstream, libarchive2 and TAR. No candidate meets the complete stable, audited, bounded-memory, self-hosted and recovery-kit requirements. The prior external scratch TAR pin 0.4.44 was upgraded to patched 0.4.46 after RustSec advisories CVE-2026-33055/33056; the scratch's custom extractor did not call the specifically vulnerable `unpack_in` helper, but the old parser version still fell below the upstream fix floor. The isolated 0.4.46 round-trip/security-fixture run passes; this is not a product dependency approval.
- CMS is a mature standards-track format but the documented Rust `openssl` 0.10.81 wrapper encrypts from a byte slice and decrypts into a `Vec`; OpenSSL documents that its CMS BIO API has streaming encoding but no corresponding inverse streaming decoder. A custom low-level bridge would add unsafe/native integration and patched-runtime obligations; CVE-2026-34182 affected OpenSSL CMS AuthEnvelopedData in supported branches until their fixed releases. CMS therefore remains a research lead, not a selected backup format.
- Libsodium's C `secretstream` API is established (introduced in 1.0.14) and streaming/AEAD, but it is a primitive/wire stream rather than the complete backup/archive and recovery-key format. `libsodium-rs` 0.2.4 is a recent Rust wrapper and requires assessment of its native libsodium build/distribution path; no Puxiri framing or key-kit profile is approved. `libarchive2` 0.2.1 binds mature libarchive but is a young Rust binding and introduces system-library/build and broad-format attack-surface questions.
- Evidence 114 refines the libsodium lead using `libsodium-rs` 0.2.5 (published 2026-09-25; Rust 1.88) and `libsodium-sys-stable` 1.24.0 metadata/docs. Upstream secretstream's XChaCha20-Poly1305 API (available since libsodium 1.0.14) authenticates each bounded message, detects removal/reordering/modification, and requires a final tag; this is a promising streaming primitive. A 32-byte randomly generated data-encryption key could in principle be wrapped to an offline X25519 recovery public key with libsodium sealed-box API, whose operation is one-message rather than streaming. The two APIs still do not define a backup format: Puxiri would need a versioned header, recipient/key envelope, bounded chunk framing/lengths, final-EOF/trailing-byte rules, manifest binding, key import/export, and atomic staged restore. This is a narrow application protocol proposal, not a standard interoperable container; it would need explicit product/security review rather than treating primitives as a format. The published Rust wrapper is recent, and its README's system-install guidance is at odds with `libsodium-sys-stable`'s documented source-build fallback; source-build/static single-binary feasibility and supported target/patch policy must be verified in an isolated build before even a candidate decision. GnuPG/OpenPGP interoperability is not provided by this design. No dependency or product code was changed and no format is selected.

- Evidence 116 extends the isolated spike with a portable recovery-key kit and a distinct restore subprocess. - Evidence 96 qualifies the static OpenSSL result: crates.io's current `openssl-src` versions list (queried 2026-10-06) has 300.6.1+3.6.3 as the newest 3.x source crate, while the official OpenSSL 3.6.4 security release is dated 2026-08-25. The static scratch therefore embeds 3.6.3, not current 3.6.4; official 3.6.4 release notes enumerate multiple fixes, including CVE-2026-54876 and CVE-2026-63072. No reachability analysis was performed, so do not infer those paths are exploitable through Sequoia; do treat the source lag as a patch-management blocker. `cargo audit` on RustSec snapshot did not report embedded OpenSSL source CVEs. A patched vendored/static build or supported system-OpenSSL dynamic build must be proven before adopting this route. No product dependency change.
- Evidence 97 source-reviews Sequoia 2.4.1 RFC9580 Argon2 S2K handling. Parser accepts byte-sized `m,t,p`; `S2K::derive_key` computes memory as `2u32.checked_pow(m)` KiB and passes parameters to argon2 0.5.3. This rejects exponent `m>31` by overflow but allows a theoretical `m=31` = 2,147,483,648 KiB (~2 TiB); `t,p` values up to 255 are accepted by the wire type and Argon2 crate limits are much higher than application policy. Sequoia's `Blocks::new` uses fallible `alloc_zeroed`, but no bounded per-request/concurrent resource policy is applied there. No high-cost parameters were executed. Public `SKESK::s2k()` exposes content KDF parameters. For encrypted secret keys there is no direct `Key::s2k()` method: callers can inspect `Key::secret()` and match `SecretKeyMaterial::Encrypted(encrypted)`, then read `encrypted.s2k()` before `decrypt_secret`. Applications must strictly allowlist S2K profile/cost and bound concurrency before deriving from untrusted data. This is a source/API review, not a demonstrated exploit or finding against the library, and does not establish OOM behavior of the host allocator. No product change.
- Evidence 98 inspects Sequoia's secret-key protection path used for the v6 recovery-key portability test. `CertBuilder` encrypts generated secret material via `encrypt_in_place`, whose default calls `S2K::default`; for v6 this is iterated SHA-256 at the max representable `0x3e00000` count (~65 MB of hash input, about 62 MiB), not memory-hard Argon2. `SecretKeyMaterial::encrypt_in_place_with` takes an explicit `S2K`, symmetric cipher and optional AEAD, so callers can choose a different protection profile; no Argon2 profile/UX has been selected for Puxiri. This means the key portability test proves passphrase-protected import/export, not approved recovery-key KDF strength. No secret/user data or product changes.
- Evidence 99 exercises that explicit route in isolated scratch. A synthetic Sequoia 2.4.1 RFC 9580 v6 Ed25519/Cv25519 keypair had each secret packet reprotected using explicit Argon2 S2K `t=2,p=1,m=16` (64 MiB), AES-256 and OCB, with fixed test-only salt. OpenPGP.js 6.3.1 parsed the serialized transferable secret key, rejected a wrong passphrase, unlocked it with the fixture passphrase, and decrypted an 8 MiB Sequoia recipient-encrypted stream; Sequoia independently decrypted the stream and both bytewise comparisons passed. This proves API and version-scoped interoperability for this intentionally synthetic low-cost profile, not strength/entropy of chosen parameters, secure salt generation (test salt is fixed), production recovery-kit policy/UX, GnuPG, other clients, or long-term portability. Scratch fmt, Clippy `-D warnings`, all 7 tests, release build passed against system dynamic OpenSSL 3.6.4 using a separate target directory because `/tmp` was full; no product changes or dependencies.
- Evidence 100 directly compiles and exercises Sequoia's preflight access route on that Argon2-protected key: match `key.secret()` as `SecretKeyMaterial::Encrypted(encrypted)` and read `encrypted.s2k()` to assert `Argon2(t=2,p=1,m=16)` before calling `decrypt_secret`. This corrects the convenient but inaccurate `Key::s2k()` shorthand in evidence 97; the direct method does not exist. The focused test passed. This confirms caller inspection is possible, not that it is enforced automatically by Sequoia.
- Evidence 101 reviews OpenPGP.js 6.3.1 Argon2 resource controls. Its configured default output profile is `t=3,p=4,m=16` (64 MiB), but `maxArgon2MemoryExponent` defaults to 30 (=1 TiB) and its explicit check in `Argon2S2K.produceKey` applies to both encrypt/decrypt; it rejects larger `m` before invoking the Argon2 WASM module. Thus the hard-coded default ceiling is vastly larger than the default profile and must be lowered explicitly for untrusted recovery keys. This documented cap only bounds memory exponent; no source evidence found in this review for a corresponding cap on untrusted `t` or `p`, and no extreme parameters were run. This is version-scoped source review, not a vulnerability or suitability claim.
- Evidence 102 runtime-checks that configuration guard without invoking high-cost Argon2: the scratch creates a v6 secret key using S2K `m=16` (64 MiB), then a separate OpenPGP.js 6.3.1 harness sets `maxArgon2MemoryExponent=15` (32 MiB) and tries `decryptKey`. It rejects with wrapped message `Error decrypting private key: Argon2 required memory exceeds config.maxArgon2MemoryExponent`; source order places this guard before Argon2 WASM invocation. The same fixture passes the normal configured cap for decrypt, wrong passphrase is rejected, and Sequoia/OpenPGP.js stream comparisons pass. This verifies the caller-configurable m cap on this version, not t/p caps, concurrent limits, actual process peak RSS, or production policy. Scratch fmt/Clippy/all 7 tests/release build passed on system dynamic OpenSSL 3.6.4; no product code/dependency.
- Evidence 103 replaces fixed test-only salts with a fresh 16-byte salt from Sequoia's documented `crypto::random` CSPRNG separately for the generated v6 primary and encryption subkey. The synthetic protected key remains interoperable with OpenPGP.js 6.3.1 (including cap-preflight, wrong-passphrase rejection and successful stream decryption); the test asserts both salts are present and unequal. This exercises a realistic salt-generation API path, but does not select Argon2 costs/profile, validate entropy/OS RNG failure handling in deployed targets, or approve recovery UX/kit. All scratch fmt, Clippy, 7 tests and release build passed; no product dependency.
- Evidence 104 inspects the bundled OpenPGP.js 6.3.1 Argon2 WASM implementation's memory/lifecycle beyond its configured exponent ceiling. `setupWasm` creates one `WebAssembly.Memory` per loaded module with `maximum: 65536` 64-KiB pages (4 GiB), so many costs allowed by the exponent hard cap (`m` up to 30 = 1 TiB) cannot actually fit and will fail allocation; the module translates known memory-growth errors to `Argon2OutOfMemoryError`. The synchronous `computeHash` call writes/clears the shared WASM memory in one JS realm and cannot overlap with another event-loop callback during its synchronous section; WASM is module-cached. After a completed call with decoded memory > `2<<19` KiB (1 GiB), OpenPGP.js schedules a module reload to enable deallocation. This is implementation-source behavior, not measured RSS/cgroup or a cross-worker/process/global concurrency limit; separate workers/processes have independent instances. Low application cap and deployment-level worker budgeting remain necessary. No high-cost input executed.
- Evidence 105 source-reviews the OpenPGP.js 6.3.1 Argon2 parameter parser/validator for CPU bounds. `Argon2S2K.read` copies wire `t,p,m` bytes; `produceKey` enforces the configured memory exponent only. Bundled `argon2id.validateParams` checks `memorySize >= 8*parallelism` and byte lengths, but no explicit pass/parallelism maximum; the synchronous implementation loops `pass < ctx.passes`. Therefore an input can request up to 255 passes in this wire profile, potentially multiplying CPU work while respecting a low memory cap. No extreme/high-pass input was run. This is code-path/source evidence, not a timing result or vulnerability classification. Treat Argon2 parameters as an exact allowlisted profile before key unlock; memory cap alone is not CPU bound. No product change.
- Evidence 106 extends the scratch preflight harness to inspect OpenPGP.js 6.3.1's parsed private-key packet objects before unlock. For the generated v6 certificate, the primary packet and one subkey both expose `s2k.type`, `t`, `p`, `encodedM`, and `salt`; the harness asserts Argon2 `t=2,p=1,m=16` for both and distinct salts before exercising the configured `m=15` rejection. This demonstrates a version-scoped caller inspection route to implement an exact S2K allowlist without deriving first. It is not a supported stable public-policy API guarantee, and does not bound work in other packet/message paths. Scratch fmt, Clippy `-D warnings`, all seven tests and release build passed; no product code/dependency.
- Evidence 107 exercises the configured OpenPGP.js 6.3.1 memory ceiling on both secret-key decryption and encryption. With `maxArgon2MemoryExponent=15`, decrypting the synthetic Argon2 `m=16` key rejects before WASM derivation. A separate copy is unlocked under normal limits, then `SecretKeyPacket.encrypt` is called with Argon2 output `m=16`, AES-256/OCB, and cap `m=15`; that also rejects with the memory-cap error before derivation. The harness includes AEAD configuration, required by this profile. Exact-profile field inspection, distinct salts, normal unlock/stream interoperability and wrong-passphrase rejection still pass. This is a runtime test of this package/version's input and output cap paths, not a policy selection or global resource bound. Scratch fmt, Clippy `-D warnings`, all seven tests and release build passed; no product code/dependency.
- Evidence 108 mutates only a disposable serialized secret-key S2K pass-count octet from 2 to 255, leaving salt, `p=1`, `m=16`, encrypted secret bytes and packet lengths unchanged. Sequoia 2.4.1 parses the modified transferable certificate and exposes the Argon2 `t=255,p=1,m=16` parameters through `SecretKeyMaterial::Encrypted(...).s2k()` without a derivation attempt. No decrypt/unlock is called on the mutated key, avoiding the deliberately expensive CPU work. The normal unmodified fixture still passes interop. This proves parser-level acceptance plus caller-visible preflight for this packet/version, not cryptographic validity of the modified secret material, exploitability, or resource impact. Scratch fmt, Clippy, all seven tests and release build passed; no product code/dependency.
- Evidence 109 repeats the parse-only mutation independently for the Argon2 parallelism octet: starting from the untouched `t=2,p=1,m=16` synthetic key, set only `p=255`; Sequoia 2.4.1 parses the certificate and exposes `t=2,p=255,m=16` through the encrypted-secret S2K accessor. The mutated key is never unlocked, so no Argon2 allocation/derivation is performed. It does not establish that Argon2 derivation would accept the tuple, that the modified secret material is decryptable, or any exploit/resource impact. - Evidence 110 performs the same parse-only mutation for `m`, changing only the memory-exponent octet from 16 to 31 while retaining `t=2,p=1`.
