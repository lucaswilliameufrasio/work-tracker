# ADR 0002: Backup archive format selection is deferred

- **Status:** Deferred — security and product compatibility evidence required
- **Date:** 2026-10-06
- **Context:** `docs/development-plan.md`, backup sections 12.2–12.3 and Phase 0 evidence 6–8, 45–46, 49, 51–53, 56–57, 60–62, 69–70, 79–89

## Context

Puxiri backups must remain self-hosted and usable in the single Rust binary. A full bundle must stream the SQLite snapshot and pinned remote files, compress/encrypt with bounded memory, restore into an isolated staging area, and support an offline recovery kit. Production must not require a Node runtime or an external archiver process. Paths, archive entry types/sizes, checksums, publication, interruption recovery and key custody are part of the format boundary.

The existing complete-bundle tests are a Node Phase 0 harness, not production code. A separate Rust scratch spike combined `tar` 0.4.44, `flate2` 1.1.9 with the pure-Rust backend, and `age` 0.12.1 streaming APIs. It encrypted/decrypted 128 MiB of synthetic data under a 1 CPU/1 GiB cgroup, verified the payload, and rejected a wrong identity and modified ciphertext. A follow-up used the Go `filippo.io/age` v1.3.2 reference CLI: Go decrypted and validated the Rust-produced 128 MiB TAR+Gzip stream, while Rust decrypted a short Go-produced ciphertext. This establishes stream-level v1 interoperability for these fixtures, not a Puxiri archive round-trip. The `age` crate explicitly remains beta before 1.0; neither implementation was tested with Puxiri snapshots, S3 pins, restoration policy or recovery keys.

## Decision

The user requires a stable, mature format and dependency API; pre-1.0/beta encryption libraries are not acceptable for selection. Do not select a production archive format or add `age`, `tar`, or compression/encryption dependencies to the product yet. Keep the current Node bundle harness experimental and retain all backup/restore requirements. Do not implement a custom general-purpose encryption/container protocol as a shortcut around the candidate's maturity status.

The Rust `age` crate is excluded under the user's stability criterion. Sequoia OpenPGP 2.4.1/RFC 9580 is a possible *encryption-layer* research lead, not an approved backup candidate: its versioned 2.x crate has documented streaming serializer and decryptor APIs for the IETF OpenPGP message format, but does not define Puxiri's archive manifest, SQLite/S3-pin transaction, staging or publication. Its current published status page (dated 2024-10-02) says it had not been audited at that time; this is stale evidence, not proof of current audit state, and no later independent audit was established here. CVE-2026-42784 describes key-flag confusion/signature forgery; Debian tracks upstream fix commit `58214b47…` in 2.3.0, before current 2.4.1, but an advisory does not establish an independent audit. Default crypto-nettle uses native Nettle; alternative native backends have distinct deployment burdens, while Sequoia says RustCrypto does not yet provide the same security guarantees as mature crypto backends. The crate is LGPL-2.0-or-later; distribution obligations need review. No format or encryption dependency is selected. Any candidate must prove build/distribution compatibility, a narrowly allowlisted modern authenticated-encryption profile, recovery-key import/export, secure allowlisted restoration, full SQLite snapshot plus pinned-object round-trip, crash/disk-full behavior, atomic publication and cgroup resource bounds before selection.

## Consequences

- No production backup format, endpoint, migration or restore flow is approved by this ADR.
- The Rust age/TAR result is feasibility evidence, not production security approval or a capacity claim.
- Age v1 stream interoperability with the Go reference implementation is verified only for the synthetic fixtures recorded in evidence 49; this does not approve the beta Rust crate or complete bundle format.
- Evidence 51 measures one synthetic Rust archive/snapshot/object composition and isolated restore on tmpfs and local Btrfs; it does not exercise the Puxiri pin/S3 protocol, production manifest or failure contracts, and is not a format selection or capacity claim.
- Evidence 52 rejects a wrong identity and a modified final ciphertext byte in that scratch archive; it does not approve the Rust crate or product publication/recovery behavior.
- Evidence 53 uploads/downloads the synthetic archive with an explicit checksum to disposable local MinIO and restores the downloaded bytes; it does not test presigned/browser flow, S3-provider compatibility, Puxiri pins, or a production manifest.
- Evidence 56 rejects a one-byte-truncated completed archive when the Rust age stream is drained; this is not a matrix of truncation points or product staging/crash behavior.
- Evidence 57 rejects one authenticated relative traversal path before opening an extracted file; it is a scratch allowlist probe, not a complete archive-path security review or product staging implementation.
- Evidence 60 rejects a duplicate path in an authenticated scratch archive. Evidence 61 adds process-level staging cleanup after the tested path-traversal and duplicate-path rejections, with a regression that first failed against the scratch implementation before the guard was added. These do not establish cleanup after process death, resistance to local path races, or product restore safety.
- Evidence 62 records the user's stable-only criterion and a source-level Sequoia review. This is candidate triage only; Sequoia is not audited per its published status page, and no archive or cryptographic profile is selected.
- Evidence 69 compares CMS/OpenSSL, libsodium secretstream, libarchive2 and TAR. No candidate meets the complete stable, audited, bounded-memory, self-hosted and recovery-kit requirements. The prior external scratch TAR pin 0.4.44 was upgraded to patched 0.4.46 after RustSec advisories CVE-2026-33055/33056; the scratch's custom extractor did not call the specifically vulnerable `unpack_in` helper, but the old parser version still fell below the upstream fix floor. The isolated 0.4.46 round-trip/security-fixture run passes; this is not a product dependency approval.
- CMS is a mature standards-track format but the documented Rust `openssl` 0.10.81 wrapper encrypts from a byte slice and decrypts into a `Vec`; OpenSSL documents that its CMS BIO API has streaming encoding but no corresponding inverse streaming decoder. A custom low-level bridge would add unsafe/native integration and patched-runtime obligations; CVE-2026-34182 affected OpenSSL CMS AuthEnvelopedData in supported branches until their fixed releases. CMS therefore remains a research lead, not a selected backup format.
- Libsodium's C `secretstream` API is established (introduced in 1.0.14) and streaming/AEAD, but it is a primitive/wire stream rather than the complete backup/archive and recovery-key format. `libsodium-rs` 0.2.4 is a recent Rust wrapper and requires assessment of its native libsodium build/distribution path; no Puxiri framing or key-kit profile is approved. `libarchive2` 0.2.1 binds mature libarchive but is a young Rust binding and introduces system-library/build and broad-format attack-surface questions.
- Evidence 70 identifies Restic's repository format as a stronger mature-format lead: Restic 0.19.1 is actively released, documents repository format v2, append-only objects, pack/index/snapshot ordering, and password-protected multiple keys. However, this is a multi-object repository protocol, not the single self-contained encrypted bundle defined in section 12.2. The Rust library `rustic_core` 0.13.0 reads/writes that format and offers backup/restore APIs under Apache-2.0/MIT, but its own crate documentation explicitly calls the API early-stage and subject to change; it does not meet the user's stable dependency-API bar today. Using the mature Go `restic` binary as a subprocess would violate the single-binary/no-external-archiver constraint. No candidate is approved.
- Restic's documented data encryption is AES-256-CTR plus Poly1305-AES, with keys protected by password-derived key files; this is established implementation practice but is not an IETF-standardized AEAD profile. The exact cryptographic profile, implementation review, key-recovery workflow and whether a repository protocol can replace the plan's self-contained full bundle require explicit security/product review. Repository integrity/order properties do not by themselves prove Puxiri's SQLite snapshot, S3-pin, staging, publication, retention or crash contracts.
- Evidence 79 updates the Sequoia lead: crate 2.4.1 documents streaming serialize/decrypt APIs over RFC 9580, a stable IETF message standard, but is only an encryption-envelope possibility. Sequoia's low-level crate explicitly avoids choosing downstream trust/use policy; its published status page says “not audited yet” as of 2024-10-02 (current audit status not established). The CVE-2026-42784 key-flag/signature issue is tracked by Debian as fixed upstream in 2.3.0; 2.4.1 postdates that tag, but this says nothing about independent audit or future advisories. Default Nettle/native build, non-recommended RustCrypto security guarantees, LGPL-2.0-or-later obligations, and passphrase/recovery policy remain unresolved. No complete archive or cryptographic profile is approved.
- Evidence 80 compiles an isolated API smoke only after opting into Sequoia's `crypto-rust`, `allow-experimental-crypto`, and `allow-variable-time-crypto` flags. A synthetic 8 MiB file round-trips through the stream writer/reader with AES-256 + OCB, wrong passphrase and a damaged final byte fail, and the scratch wrapper withholds rename/publication on failure. The default Nettle backend did not build because this host lacks the Nettle development header `nettle/pgp.h`; no system package was installed. Because the only successful run used a backend Sequoia explicitly calls experimental and variable-time, this is API/stream composition evidence only—not cryptographic, security, performance, memory-bound, interoperability, or production suitability evidence. The simple scratch rename also lacks production durability/hostile-path guarantees. Sequoia remains unselected.
- Evidence 81 repeats the same synthetic 8 MiB stream/tamper smoke using Sequoia's documented `crypto-openssl` backend against system OpenSSL 3.6.4; locked offline fmt, Clippy `-D warnings`, all-target tests and release build pass. The produced test binary dynamically links `libssl.so.3` and `libcrypto.so.3`, so this is not evidence for a self-contained single-binary distribution. It removes the need for the experimental RustCrypto flags on this host, but does not establish cryptographic profile safety, OpenPGP interoperability, independent audit status, supported deployment matrix, LGPL distribution compliance, memory/cgroup bounds or complete backup suitability. Backend remains unselected.
- Evidence 82 attempts external interoperability with the locally installed GnuPG 2.4.9/libgcrypt 1.12.3, without lowering Sequoia's `StandardPolicy`: GnuPG rejects Sequoia output's version-6 SKESK as unknown; Sequoia rejects GnuPG's forced-AEAD output because it is AEAD Encrypted Data Packet v0, which the current policy considers insecure. Both sides fail closed and staging is withheld. This is a real compatibility gap for these exact local versions/configuration, not proof of general RFC 9580 incompatibility or behavior in newer GnuPG; no bidirectional interoperable backup profile was established. A future candidate needs independent-tool interoperability with current supported versions and an explicitly reviewed compatibility policy.
- Evidence 83 proves bidirectional synthetic stream compatibility between Sequoia 2.4.1 (`crypto-openssl`) and OpenPGP.js 6.3.1 on Node 24.21.0 when both explicitly use RFC 9580 AEAD OCB/AES-256: OpenPGP.js decrypts Sequoia output and Sequoia decrypts OpenPGP.js output under their standard policy/default S2K choices. This is a single 8 MiB fixture and does not establish interoperability with GnuPG, archival profile suitability, external audit, passphrase/KDF strength, complete bundle semantics, or production security. OpenPGP.js is a distinct implementation, but its AEAD path is behind an explicit opt-in and its LGPL-3.0 license is an additional test-only/tooling fact, not a product choice. No JS package or Rust crate was added to the checkout.
- Evidence 84 reviews actual passphrase-S2K defaults and verifies the interoperable Argon2 option in a one-way synthetic fixture. Sequoia 2.4.1's `S2K::default()` uses salted+iterated SHA-256 at the maximum representable count `0x3e00000` (65,011,712 input bytes, about 62 MiB of hashing; not memory-hard). OpenPGP.js 6.3.1 defaults to iterated S2K coded count byte 224 (16 MiB of hashing; also not memory-hard), but supports RFC 9580 Argon2 S2K when explicitly selected; its documented defaults are `t=3,p=4,m=2^16 KiB` (64 MiB RAM). With those defaults, OpenPGP.js encrypted an 8 MiB synthetic stream and Sequoia decrypted it successfully. RFC 9580 recommends Argon2 and permits iterated+salted S2K when Argon2 is unavailable with a high count and strong passphrase. This does not select Argon2 params for Puxiri, assess entropy/UX or concurrent memory/DoS bounds, test recovery over time, or establish GnuPG compatibility for this exact packet profile.
- Evidence 85 inspects the official GnuPG 2.5.24 source tarball, the current stable release listed on gnupg.org on 2026-10-06, without building or executing it. `g10/parse-packet.c::parse_symkeyenc` accepts SKESK versions 4 and 5 only and S2K modes 0, 1, and 3 only; version 6 and Argon2 mode 4 are rejected by source control flow. This independently corroborates the local GnuPG 2.4.9 fixture gap and shows that RFC9580 v6 SKESK/Argon2 interoperability cannot be claimed for the current official GnuPG stable source. It is a source inspection, not a runtime test, and says nothing about other OpenPGP clients or future GnuPG changes. The upstream tarball was fetched over HTTPS; no system software was installed and no user data/keys were used.
- Evidence 86 evaluates rPGP 0.21.0 (MIT OR Apache-2.0, pure Rust) as a second RFC 9580 envelope implementation. Its low-level API has `Read`/`Write` message paths and supports SKESK v6, SEIPDv2 OCB and Argon2 S2K; its own implementation status says the high-level API is not started. An isolated 8 MiB file-streaming harness using Argon2id `t=3,p=4,m=64 MiB`, AES-256/OCB passed bidirectionally with OpenPGP.js 6.3.1 using the same S2K/AEAD profile. Tampering with the last byte made decrypt return an authentication error, but 8,110,080 plaintext bytes had already reached the harness output file before final-tag verification. Any caller must write exclusively to private staging and publish only after complete EOF and success; this test is not atomic restore behavior. Source inspection shows an Argon2 parser cap of 2 GiB per derivation and `t,p<=32`, which does not establish a safe concurrent-memory bound. The crate reports a 2024 Radically Open Security audit with listed findings fixed, but its current `SECURITY_STATUS.md` also lists an unresolved Marvin/side-channel concern in its RSA dependency; the symmetric password-only test does not exercise RSA. The harness uses no public-key RSA, tests only one client pair/profile, and does not establish GnuPG interoperability (evidence 85's parser limitation still applies), complete bundle semantics, bounded RSS, independent current review, or suitability. No crate or code was added to Puxiri.
- Evidence 87 inspects rPGP 0.21.0's public `Message::Encrypted { esk, .. }`, `Esk::SymKeyEncryptedSessionKey(packet)`, and `packet.s2k()` API: callers can inspect and reject S2K parameters before invoking the convenience `decrypt_with_password`, which derives directly from packet parameters. The crate's own `Message` docs warn plaintext may be arbitrarily large and recommend a limiting reader, but explicitly require treating a read that stops at the limit with unread input as unsuccessful. Therefore a size cap cannot be treated as successful authenticated EOF: caller must reject overflow while still draining/validating the full AEAD stream or keep all output private and discard it. This is a source/API feasibility observation, not a test that a complete safe preflight/limit wrapper has been implemented.
- Evidence 88 exercises the recovery-key path at API level in the isolated rPGP harness: it generated an ephemeral OpenPGP v6 Ed25519 primary plus X25519 encryption subkey, encrypted an 8 MiB synthetic file with PKESK v6/SEIPDv2 OCB/AES-256, decrypted and compared bytes. This demonstrates an in-process RFC 9580 public-key encryption route compatible in concept with the plan's offline private recovery key. It does not serialize/import the private key across processes, test encrypting/protecting the recovery-kit private key, OpenPGP.js/GnuPG interoperability, key rotation/loss, authenticated manifest metadata, cgroup bounds, or the complete archive. The generated key is disposable synthetic material; no product dependency or implementation was added.
- Evidence 89 extends the isolated harness to serialize the generated v6 private recovery key, import it in a separate process, decrypt the synthetic 8 MiB bundle and compare byte-for-byte. The v6 key builder uses its documented default secret-key protection: Argon2id `t=3,p=4,m=64 MiB` and AES-256/OCB. Wrong key passphrase returned `MissingKey` before the harness created an output file. This is a useful kit-portability/API smoke, not a recovery UX, permissions, multi-host, interoperability, rotation/loss or product atomic-publication test; the secret artifact contains only disposable synthetic key material and fixtures.
- Phase 0 backup/restore and resource checkboxes remain open until the end-to-end contracts above are verified and recorded.
- S3 remains optional; a backup's key custody and restored destination credentials remain separate from this format selection.
